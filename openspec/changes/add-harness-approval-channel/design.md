# Harness approval channel

Resolve one Proceed request through Telegram or a separately authorized local operator interaction, without giving the agent decision authority.

## Status and boundary

**Amended contract complete for bounded helper implementation and qualification, not broad production or landing readiness.** Use a client-only TUI interaction and a separate operator credential enrolled through the existing paired-human authority. The TUI delegates each broker exchange through a private parent-created pipe to a short-lived application-owned Node >=24 helper. Only that helper performs the unchanged TLS-PSK exchange. The pinned SDK supplies the generic UI primitives. Actual compiled OpenCode v2.2.5/helper composition, authority separation and concurrent-session routing remain unqualified.

## Settled system boundaries

| Component                     | Responsibility                                                                                            | Authority excluded                                                                                      |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Broker                        | Durable requests, session admission, authorization, expiry, single winning resolution and delivery ledger | Executing the requested action                                                                          |
| MCP adapter                   | Existing preparation/wait/retrieval interaction and original JSON-RPC response destination                | Converting agent arguments, ordinary form replies or session labels into operator authority             |
| Qualified harness integration | Bind the invoking session to the request and display the broker's immutable question                      | Selecting the foreground session as a substitute route                                                  |
| Local operator UI             | Obtain an explicit request-bound choice through a configured trusted client interaction                   | Treating a command argument, service form record or caller's human flag as a human choice               |
| One-exchange Node helper      | Carry one TUI-authorized harness operation over the existing protected TLS-PSK broker connection          | Loading operator keys, supplying human choices, exposing a service or obtaining owner/control authority |
| Telegram adapter              | Existing paired-human decision path                                                                       | Creating a second approval for the mirrored question                                                    |

The local operator is an additional authorized decision-maker. No proof that this operator is the paired Telegram person is required. The trusted account, trusted UI and operator-controlled installation remain assumptions. Protection against a compromised UI, same-account malware, debugger access or deliberate credential extraction is not promised.

That limitation does not excuse ordinary agent self-reply through supported host APIs. The qualification threat case is an agent using its normal Shell/API tools and the host's ordinary configured service authentication, without extracting a separate operator secret or compromising the trusted UI. That agent must be unable to resolve Proceed requests. Capability negotiation, transport authentication and correct response correlation do not establish this separation.

## 1. Client-only interaction and independent operator authority

The OpenCode integration SHALL be a TUI-only plugin, loaded through the documented CLI plugin configuration, not a server decision RPC. Native MCP elicitation is not used for this decision path. Form `accept` means submission, not domain Approve or operator provenance. An ordinary form reply, service API user record or plugin RPC authenticated as the host client cannot grant Proceed decision authority.

Use a two-step local interaction: select a host session, then open that session's broker-bound question. Use `ui.dialog.select` for session navigation and Approve/Reject/Respond, and `ui.dialog.prompt` for Respond text. Approve SHALL NOT be the initial highlighted option. The complete question SHALL be currently rendered alongside the decision controls, not merely shown earlier in navigation. Use `ui.dialog.show` when needed to satisfy that display requirement. Dismissal or `undefined` sends no decision. Session selection and command dispatch are navigation only, not an answer or a routing mutation. Only completion of the local request-bound choice interaction may invoke the product decision client. Command arguments, server events and RPC inputs cannot supply or settle its answer.

The TUI SHALL use only its private one-exchange Node helper to reach the broker, never the OpenCode service for operator authorization. Its nonsecret configuration remains exactly `state_dir`, `harness_id`, `owner_id`, `operator_key_file`. Both IDs match `[a-z0-9_-]{1,64}`. `owner_id` must name an existing configured principal, and `harness_id` names one operator-configured local OpenCode service installation. The first supported topology is local TUI, local OpenCode service, local Node and local broker on the same account/machine. Remote service/TUI operation is not qualified. A harness identity cannot silently be reused for another service installation.

The independent operator credential is `hop_` plus 64 random lowercase hexadecimal characters. `key_id` is the lowercase SHA-256 hexadecimal digest of the complete credential string. It is a public fingerprint and verifier, not sufficient authority by itself. Broker state stores only this verifier. The TUI alone loads the private file and retains the credential in its process-local closure. For an admitted exchange only, it transmits a transient copy through its private child pipe. Neither process SHALL place it in argv, environment, files, stdout, stderr, diagnostics, synchronized `storage.store`, host service storage, RPC, tool results or model-visible arguments. No CLI command auto-loads an enrolled operator key to submit decisions or issue replacement authority. The owner's ordinary control/request credentials remain insufficient for decisions or enrollment acceptance.

This introduces a transient second memory copy in a trusted application-owned process and pipe buffers. Release references and clear mutable secret buffers on completion or abort, without promising complete garbage-collected-memory erasure. Private pipes prevent ordinary supported Shell/API traffic from acquiring authority, not same-account memory inspection, debugger access, malicious runtime replacement or deliberate extraction. Parent PID, helper invocation, host Basic authentication and possession of this protocol are not human attestation or operator authority.

`proceed-mcp harness keygen --operator-key-file <absolute-file>` SHALL create one new protected credential file containing exactly the credential plus LF. It takes no secret argument, refuses existing destinations and never reads, replaces or signs with an existing key. It neither enrolls a key nor approves work. Apply the startup dependency's protected credential-directory, current-account ownership, no-redirection, single-link, pre-write protection and exact-owned failure-cleanup rules. Keep this file outside repositories, broker state and MCP configuration. The TUI verifies those protections and actual file identity before loading. Its configuration carries only the path. No automatic import, secret export or credential-recovery command is added.

Successful key generation exits `0` and reports only the nonsecret destination and `key_id`. Invalid options or an existing destination exit `2`/`INVALID_ARGUMENT`. Unsafe or unverifiable protection exits `4`/`PROTECTION_UNVERIFIED`, and failed durable creation exits `4`/`STORAGE_FAILURE`. No success is reported before flush and final identity/protection checks. This design authorizes no access to existing operator, Telegram, control or owner credentials during development or qualification. Synthetic fixture authority is sufficient.

### Enrollment: authorization before the first decision

An explicit local UI setup action submits a proposed `(harness_id, owner_id, key_id)` enrollment. The UI displays that public fingerprint and the broker-issued enrollment ID. The paired human then sends `/harness <enrollment_id>` privately to the bot. The broker shows the proposed scope and fingerprint and asks explicitly whether to authorize that local operator key. The human must compare it with the genuine TUI setup display before confirming. A chat message, owner/control API call, synthetic user record or request capability alone cannot confirm enrollment.

This is a one-time delegation of decision authority, not a work approval and not an extra reviewer on subsequent requests. It does not prove or require that the local operator is the paired Telegram person. Another local operator can use the enrolled UI thereafter without contacting Telegram for each decision. The security cost is an additional protected local secret and explicit paired-chat confirmation during enrollment. Re-enrollment needs that confirmation again. This uses the existing paired-human setup authority rather than silently allowing agent self-enrollment or introducing cloud identity.

Enrollment is bound to the existing pairing identity and exact principal. The broker SHALL retain at most one pending enrollment per owner, for 300 seconds. Identical replay returns it without extending expiry. A different proposal receives `409`/`ENROLLMENT_BUSY`, never replacement. At most one active key is allowed per `(harness_id, owner_id)`. A different key receives `409`/`OPERATOR_ALREADY_ENROLLED` until the paired human explicitly revokes the old key using `/harness_revoke <key_id>`. Revocation removes decision authority, not retained outcomes or pending Telegram access. A consumed, rejected, expired or old-pairing confirmation cannot enroll anything. Enrollment messages and UI show fingerprints, never the credential.

Reuse the existing private-chat command and inline-callback transport. Enrollment Confirm/Deny callback data is respectively `he:<token>`/`hx:<token>`, where each token is 32 random lowercase hexadecimal characters mapped durably to that enrollment and its pairing snapshot. As with request callbacks, tokens correlate an interaction but confer no authority without the independently validated paired sender/private chat. Validate current pairing, enrollment scope, pending state and expiry atomically before accepting Confirm. Deny closes only that proposal. These callbacks cannot enter the request-resolution parser. Duplicate Telegram updates have no second enrollment effect. Revoke is accepted only from the current paired human/private chat and is idempotent. No control or owner HTTP endpoint can confirm, reactivate or replace a key.

### Reload and exit

Each plugin setup generation owns its transports, timers, session picker and question/response dialog callbacks. Returned `Cleanup` fences that generation before aborting resources. Late picker completions cannot open a question, and late decision completions cannot submit. Dismissal, replacement or disposal of an interaction fences its callbacks without cancelling the durable request. Reload may reread the protected file and use its still-enrolled key, but must refresh pending state and create fresh local dialogs for retained presentation bindings. Do not retain resolved dialog promises as permission. TUI exit loses local interaction state, not durable requests or enrollment. A genuinely new TUI may explicitly reopen the same session's pending question, without claiming that the old process resumed or redirecting an old waiting result.

## 2. Product-owned secure wire contract

All routes below retain the merged startup contract's exact authenticated TLS-PSK origin `https://127.0.0.1:<configured-port>`. The TUI reads the configured protected configuration and operator key. The helper reads only the explicitly handed-off protected schema-2 `broker.lock` for instance trust, never the operator key file or owner/control/Telegram credentials. On every new connection, require the stable protected lock, TLS 1.2 only, sole cipher `PSK-AES256-GCM-SHA384`, fixed public selector `proceed-mcp-local-v1`, fresh PSK callback, no session reuse and no renegotiation. Require client `rejectUnauthorized:true`, `authorized:true`, no authorization error and the startup profile's PSK-only identity check. Recompare the complete protected lock after handshake before any HTTP bytes. Preserve the 1000 ms handshake ceiling within the exchange deadline. No HTTP downgrade, proxy, redirect, extra listener, host service password or request-capability substitution is permitted. Actual compiled TUI-to-Node pipe composition and Node secure admission are qualification gates. Bun performs no TLS exchange for this operator path. Startup, broker lock, broker wire, enrollment and journal contracts are unchanged by this correction.

The new `/v1/harness/` routes use `Authorization: Bearer <operator-credential>`. Their credential role is independent of existing owner/control routes. Enrollment alone permits an as-yet-unenrolled credential to propose its own verifier. Protected channel possession is not enrollment approval. Every other route requires an active enrolled verifier before any request disclosure or mutation. Browser `Origin` remains forbidden. JSON objects reject additional fields and retain the existing 64 KiB limit. IDs remain case-sensitive. Existing request IDs and timestamps retain their formats. `enrollment_id` is `hen_` plus 32 random lowercase hexadecimal characters and `presentation_id` is `hpr_` plus 32 random lowercase hexadecimal characters.

Preserve disjoint roles: owner credentials retain reservation/request/registration access, control retains pairing/status/shutdown, and both retain `GET /v1/ready`. Operator credentials gain only the harness routes, not readiness, startup, registration, request-capability access or shutdown. A valid existing credential used on the wrong role's route returns `403`/`FORBIDDEN`. Merely knowing a transport PSK, owner ID, session ID or public fingerprint grants none of these HTTP roles. Harness calls do not acquire or renew an adapter registration. The TUI observes a broker made available by normal MCP startup and never launches, stops, repairs or takes ownership of it.

| Route                                              | Exact input                                                                        | Successful result                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/harness/enrollments`                     | `{harness_id,owner_id}`                                                            | `202 {schema_version:1,enrollment_id,harness_id,owner_id,key_id,expires_at,state:"pending"}` for a new or identical pending proposal. Already enrolled matching scope returns `200` with the same fields and `enrollment_id:null,expires_at:null,state:"enrolled"`. No request details. |
| `POST /v1/harness/pending`                         | `{harness_id,owner_id,session_id}`                                                 | `200 {schema_version:1,presentation}`. `presentation` is null or the presentation below for this exact scope/session. Poll at most once per second per displayed session.                                                                                                               |
| `POST /v1/harness/presentations/{presentation_id}` | `{harness_id,owner_id,session_id,request_id}`                                      | `200 {schema_version:1,request_id,decision_id,resolution,response_text}` for this exact retained binding. Read-only authoritative observation, including pending or terminal status. `decision_id` is null while pending.                                                               |
| `POST /v1/harness/decisions`                       | `{harness_id,owner_id,session_id,request_id,presentation_id,choice,response_text}` | `200 {schema_version:1,accepted,request_id,decision_id,resolution,response_text}` after durable resolution. `accepted` is true only for this newly committed choice, false for an already terminal request.                                                                             |

`session_id` is a nonempty well-formed Unicode string encoded as at most 512 UTF-8 bytes, compared exactly without normalization. A presentation is exactly `{presentation_id,request_id,harness_id,owner_id,session_id,session_label,action,context,expires_at}`. These values come from the broker's immutable request, never from a UI-supplied question. Display the complete action, context, deadline, request ID and caller-supplied label before a choice. Render text inertly, not as terminal control sequences or executable links. A presentation ID is correlation, not a credential.

Extend the common request representation and its MCP structured/text projection with exactly `harness_channel:{state,reason}`. `state` is `unavailable`, `eligible` or `closed`. Pending requests are `eligible` only with an enabled route and active matching enrollment, with `reason:null`. Otherwise `reason` is `HOST_NOT_CONFIGURED`, `SESSION_ROUTE_UNAVAILABLE` or `OPERATOR_NOT_ENROLLED`, in that precedence. Terminal requests are `closed` with `reason:null`. This is eligibility/status, not proof of UI display, human receipt or call delivery. Instructions explain Telegram fallback and the corresponding setup/route repair. Existing fields and outcome semantics remain unchanged. No operator fingerprint, secret or presentation authority is added to model results.

`choice` is exactly `approve`, `reject` or `respond`. `response_text` is null for approve/reject and a well-formed Unicode string of 1-4096 scalar values for respond, matching the existing response limit and retained unchanged. Any other combination is `400`/`INVALID_ARGUMENT`, with no resolution. Refresh authoritative status after a transport error rather than claiming the choice failed to commit or automatically replaying it. Explicit retry of the identical bound choice is safe, returning the retained terminal resolution with `accepted:false` if already committed. The successful `resolution` is the existing terminal enum, and `response_text` reflects the recorded result, not necessarily the submitted losing choice.

Errors retain `{schema_version:1,error:{code,message,retryable}}`. Missing/malformed operator credentials or an unenrolled/revoked key on enrolled-only routes return `401`/`AUTH_REQUIRED`. Existing owner/control credentials never count as this role and receive the wrong-role refusal above. An active key attempting a foreign scope returns `403`/`FORBIDDEN`. Unknown/mismatched request or presentation returns `404`/`NOT_FOUND` without foreign details. Invalid payload is `400`/`INVALID_ARGUMENT`, unavailable pairing is `503`/`NOT_PAIRED`, storage failure is redacted `500`/`STORAGE_FAILURE`. These are operator HTTP errors, not additions to the MCP error catalog except `SESSION_BUSY` below. Enrollment conflicts are nonretryable until expiry or explicit operator repair. Authentication precedes scope/request lookup and deadline mutation. Preserve authenticated `503`/`BROKER_NOT_READY` admission while recovering/stopping and fence new harness mutations during drain. Legacy serving gains none of these routes.

Presentation IDs survive lost responses and broker restart and are never reassigned. Terminal presentation bindings remain retained with their request. On submission the broker checks the enrolled key, its scope and complete presentation binding inside the same serialized operation as deadline/resolution. Revocation racing a submission must therefore win before decision admission or lose to an already accepted decision. Merely loading a key before revocation is insufficient. A terminal matched request returns its unchanged outcome, including when another channel won. No actor, response body or status field can change the outcome type.

Each exchange has a 10000 ms absolute deadline including executable resolution, spawn, handshake/handoff, protected reads, TLS, headers, body and cleanup admission, with a 64 KiB HTTP response ceiling. The helper protocol below reserves cleanup within that same budget. Late file-read, spawn, pipe and dialog completions cannot authorize another phase after cancellation/deadline. No new background supervisor or automatic mutation retry is added. Pending observation and harmless reenrollment observation may resume after a connection failure while the UI remains active. Stale UI closure is best effort, never the authorization boundary. Dialogs are actionable only before the immutable request deadline. At that deadline, picker/question/response dismissal, replacement or disposal, invocation cancellation, or plugin cleanup, fence the affected callbacks and abort their owned exchanges/children/timers. Picker dismissal grants no authority. A question's expiry also fences any subsequent Respond completion for that presentation. If the host cannot dismiss a dialog, its late result is inert rather than a retained permission. Abort cannot roll back a broker-committed winner. After uncertainty, a still-active or freshly opened interaction refreshes the exact retained presentation with a new read-only exchange, never automatic decision replay.

### Private TUI/helper process contract

This is an application-internal cross-process contract, not a public CLI, MCP tool, decision RPC or broker transport change. One parent-created child serves exactly one exchange and exits. No listener, named rendezvous, detach, daemon, descendant process, global queue, automatic installer or supervisor is permitted. Concurrent sessions have independent exchanges. Private implementation module structure remains unconstrained.

**Executable admission.** Resolve `node` (`node.exe` on Windows) to an absolute real executable. Use the trusted operator-provisioned TUI process PATH only as an explicit candidate list, not shell or current-directory lookup. Reject relative/empty search entries, the working directory, shell/batch wrappers and unverifiable or untrusted executable ancestry. Do not infer Node from Bun's `process.execPath`, use `fork`, inherit `execArgv` or invoke a shell. Resolve the helper relative to the installed package, never the current directory, user input, host discovery or a test fixture. Both executable and helper are trusted installation inputs with no less-trusted writable replacement path. No new plugin option or package dependency is introduced. Existing installed Node is a prerequisite, never automatically installed. Recheck their identities before spawn. The child must identify a genuine Node runtime, with no Bun runtime marker, version >=24. First qualification is exactly Node 24.22.2. Higher versions meet the minimum, not an automatic compatibility claim. Missing, unsupported or unverifiable Node disables this channel with a fixed nonsecret error, never fallback to Bun or a weaker transport.

Spawn with an explicit clean environment, not a filtered copy of the host environment. It may contain only OS-required execution variables with verified nonsecret values. On Windows this includes trusted `SystemRoot`/`WINDIR` if required. No PATH lookup is needed after resolution. No provider/host/broker credentials, proxy settings, `NODE_OPTIONS`, `NODE_PATH`, `NODE_DEBUG`, coverage, preload, inspector, loader or dynamic-library injection variables may be inherited. Arguments contain only fixed runtime flags and the absolute packaged helper path, never authority, operation data or caller-controlled flags. No debug/trace mode is admitted.

**Pipe and framing.** Use async spawn with stdin ignored, stdout/stderr privately captured as zero-output tripwires, and separate parent-created `pipe` stdio slots 3 (parent-to-child) and 4 (child-to-parent). Neither slot is inherited from the terminal, exposed to host APIs, stored by name or shared with other children. No Node/Bun serialized IPC channel is used. Keep slot 3 open as a lifetime signal after the request, not as an EOF request terminator. Parent death therefore produces EOF. Slots are byte streams, not message boundaries. Every frame is a 4-byte unsigned big-endian byte length followed by strict UTF-8 JSON with no BOM, duplicate keys or additional fields. Length is 1-81920 bytes, checked before allocation. Partial frames, malformed UTF-8/JSON, wrong order/ID/version, extra frames or trailing bytes fail closed. Total traffic is at most 98304 bytes per direction per child, including prefixes. No unbounded buffering is allowed. Any stdout/stderr byte aborts the exchange, is discarded without logging, and cannot become a diagnostic. Capture at most 4096 bytes per stream before forced close/termination, never forward raw output.

All frames have `schema_version:1`, `type` and `exchange_id`. The ID is 32 fresh random lowercase hexadecimal characters generated by the TUI, used only for correlation. Exact additional fields and order are:

| Direction / type  | Additional fields                                                                  | Admission                                                                                                                                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Parent `hello`    | `deadline_unix_ms`                                                                 | Integer absolute deadline fixed at exchange entry, at most 10000 ms away. Contains no secret.                                                                                                                            |
| Child `ready`     | `runtime`, `node_version`                                                          | `runtime:"node"`, bounded numeric release version string of at most 32 ASCII characters. Emitted only after actual runtime and private descriptors are checked. Parent validates before sending authority.               |
| Parent `exchange` | `port`, `lock_file`, `operator_credential`, `operation`, `presentation_id`, `body` | Port 1-65535 and absolute protected lock path from configured state. Credential has the exact operator format. Body and binding are validated against section 2 before any connection. No operator-key path is accepted. |
| Child `response`  | `status`, `body`                                                                   | Exactly one complete parsed broker response, status 200-599, body satisfying the applicable section 2 success/error schema. No raw headers, socket data or echoed authority.                                             |
| Child `error`     | `code`                                                                             | Instead of `response`, one fixed local error code below. No arbitrary message, stack, cause, path, environment or request fields.                                                                                        |

`operation` is exactly `enrollments`, `pending`, `presentation` or `decisions`, mapped respectively to the four existing POST routes in section 2. `presentation_id` is a valid retained ID only for `presentation` and is null otherwise. Its route is constructed locally without query, fragment or arbitrary path components. `body` is exactly that route's input table. The parent constructs decisions only from the completed genuine local choice and captured immutable presentation. The helper cannot create choices or infer a default. No URL, method, headers, proxy, owner/control token, readiness/start/stop operation or extension operation is accepted. The helper derives only the fixed origin and operator headers defined above. It never discovers or loads a key file, even when invoked from an ordinary Shell/API process. Normal invocation without a supplied operator secret and valid protected channel cannot gain authority. A public fingerprint or parent PID cannot replace that secret.

Local codes are exactly `NODE_UNAVAILABLE`, `NODE_UNSUPPORTED`, `HELPER_PROTOCOL_INVALID`, `HELPER_LIMIT_EXCEEDED`, `EXCHANGE_CANCELLED`, `EXCHANGE_DEADLINE`, `BROKER_UNAVAILABLE`, `BROKER_INSTANCE_CONFLICT` and `BROKER_RESPONSE_INVALID`. The first two may be generated by the parent before a usable helper exists. Messages shown to the UI are fixed strings selected by code, never raw runtime errors. Valid broker refusals remain `response` with their unchanged HTTP status and error envelope, not a renamed helper error. Unknown local failures map to `BROKER_UNAVAILABLE`. Exit 0 requires one valid response and complete cleanup. An emitted local error exits 1. Failure before a valid hello exits 1 without an uncorrelated frame. Missing/malformed output, nonzero exit after a response or unconfirmed cleanup is uncertainty, never accepted approval. No helper code is added to the MCP error catalog.

**Lifetime and success admission.** The parent starts its monotonic 10000 ms timer before resolution/spawn and checks it at every transition. The child starts its own monotonic timer at entry, then caps remaining time by `deadline_unix_ms`, never extends it after handoff or wall-clock change. Before hello, the child's maximum lifetime is 10000 ms. Before any protected read or network activity, reserve the final 1000 ms for cleanup. Stop active work by deadline minus 1000 ms. TLS retains its separate ceiling of min(1000 ms, remaining active-work budget), never a fresh exchange budget. If insufficient time remains, no next phase begins. The earlier immutable request deadline additionally fences decision submission. A response is usable only after its frame, clean child exit and pipe closure are admitted within the original deadline and the owning generation/interaction is still active. Do not release the lifetime pipe merely because a response frame arrived.

On parent death/slot-3 EOF, broken pipe, abort, reload, dismissal, replacement, invocation cancellation or deadline, fence callbacks first, abort protected reads and TLS/HTTP work, close owned pipes/sockets and discard late output. Late asynchronous completions must check the fence before further reads, connects or writes. The child exits within min(1000 ms, remaining lifetime) after EOF/abort. A live parent requests termination immediately when cleanup starts and escalates to forced termination by 500 ms if needed, verifying exit and closing resources by 1000 ms and within the exchange deadline. Never signal an unrelated PID or treat a successful kill request as proof of exit. Cleanup failure disables further helper exchanges for that generation and reports a fixed nonsecret failure, not success. Broker state remains authoritative if a decision committed before cancellation or pipe loss. Reload creates fresh interaction state and refreshes that exact binding, not rollback, redirected callback or replay. Platform inability to enforce these bounds blocks qualification.

## 3. Invocation and session binding

`mcp --owner <owner_id> --harness-id <harness_id>` opts this adapter principal into the configured host namespace. Omission retains Telegram-only behavior. An active matching enrollment is needed for presentation/decision access, not for portable waiting. Session metadata alone never grants this role.

For qualified host calls, read `CallToolRequest.params._meta["ai.opencode/sessionID"]` from transport metadata, not model arguments. Accept only the bounded session string above. Forward the configured harness ID and metadata value to the broker on preparation as optional local HTTP `harness_route:{harness_id,session_id}` in `POST /v1/handles`. The broker derives `owner_id` from the existing owner credential. No new model argument or decision tool is introduced. Persist the route with that reserved handle. Add the same optional `harness_route` to `POST /v1/requests` solely to check that the invoking context still matches the prepared route. It cannot retarget a handle. A supplied conflicting route returns `409`/`IDEMPOTENCY_CONFLICT`, without presentation or mutation. A missing route never substitutes the foreground session or changes the stored association.

Calls without safe metadata continue through the portable baseline without a harness presentation. If preparation had no route, later metadata cannot add one to that handle. The adapter omits the route when forwarding that creation and reports Telegram-only operation. If preparation had a route but the creating call has no safe metadata, retain the stored route for occupancy but do not expose a harness presentation until an authorized matching-context replay supplies it. Persist this presentation-enabled state. A known conflicting route is a conflict, never this missing-metadata fallback. Retain previously enabled routing on authorized replay or later metadata loss. The merged reservation body is `{session_label?}` and the creation body is `{request_handle,client_request_id,action,context,expires_in_seconds?}`. This change adds only optional `harness_route` to those bodies, preserving owner Bearer admission, `X-Proceed-Request-Capability` on creation, existing field validation and nondisclosing handle/capability denials. No route field is added to the five model-facing tool input schemas. The existing same-principal bearer-transfer model still permits authorized observation/cancellation and does not redirect an existing waiting result. Session routing is not nontransferable agent identity.

The merged one-live-adapter-per-owner registration lease remains 45000 ms with existing `OWNER_IN_USE` behavior. Distinct harness sessions multiplex through that adapter, not competing registrations for the same owner. Preserve original-call waiting, 32000 ms bounded wait exchanges, active-call reconnect and the separate 150000 ms startup availability budget. Harness UI polling or loss cannot extend any of these or the request deadline.

The TUI SHALL offer explicit selection from the documented `data.session.list()` host session list, showing each session's title and exact ID. After selection, verify that exact ID with `data.session.get` before querying pending state for only that scoped session. An unresolvable session shows no decision UI. Selection does not modify the stored request route or answer a question. Capture the broker's returned immutable presentation for every subsequent choice and Respond completion, not a reactive current-session or current-pending reference. Tab switches, foreground state, session titles, root/family membership, most-recent activity and reuse of a session's pending slot cannot retarget it. Reopening requires a fresh lookup and local interaction. Distinct sessions retain independently concurrent requests and may be selected and resolved in either order, including with equal titles or labels. Modal display serialization cannot impose a global broker admission or resolution queue. Ordinary host APIs can expose/reroute labels or cause a prompt, but cannot supply the private operator credential or settle the client-local choice.

## Request and resolution invariants

The broker SHALL enforce these rules:

- Keep the existing two-tool prepare then create-and-wait workflow and private capability model. The same request ID, action, distinguishing context and absolute deadline appear on both surfaces. Neither surface contains request capabilities, operator credentials or transport secrets.
- Bind a harness-enabled request immutably to its protected transport principal, configured harness identity and opaque host session route. Route labels never grant request access or decision authority. A retained request capability continues to authorize explicit same-principal access, not human decisions or automatic session reattachment.
- In the broker's serialized durable creation operation, enforce at most one unresolved request per `(owner_id,harness_id,session_id)`. Reservation alone is not an unresolved request. Identical authorized replay preserves request identity, content and deadline. Changed payload retains the existing idempotency conflict.
