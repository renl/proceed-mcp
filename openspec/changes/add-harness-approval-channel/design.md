# Harness approval channel

Resolve one Proceed request through Telegram or a separately authorized local operator interaction, without giving the agent decision authority.

## Status and boundary

**Design complete for a bounded qualification checkpoint, not production implementation-ready.** Use a client-only TUI interaction and a separate operator credential enrolled through the existing paired-human authority. The pinned SDK supplies the generic UI primitives. Enrollment and decision authorization are product-owned contracts, not missing native human-attestation APIs. Actual OpenCode v2.2.5 authority separation, local secure transport and concurrent-session routing remain unqualified.

Product deltas remain proposals until this change lands.

## Settled system boundaries

| Component                     | Responsibility                                                                                            | Authority excluded                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Broker                        | Durable requests, session admission, authorization, expiry, single winning resolution and delivery ledger | Executing the requested action                                                              |
| MCP adapter                   | Existing preparation/wait/retrieval interaction and original JSON-RPC response destination                | Converting agent arguments, ordinary form replies or session labels into operator authority |
| Qualified harness integration | Bind the invoking session to the request and display the broker's immutable question                      | Selecting the foreground session as a substitute route                                      |
| Local operator UI             | Obtain an explicit request-bound choice through a configured trusted client interaction                   | Treating a command argument, service form record or caller's human flag as a human choice   |
| Telegram adapter              | Existing paired-human decision path                                                                       | Creating a second approval for the mirrored question                                        |

The local operator is an additional authorized decision-maker. No proof that this operator is the paired Telegram person is required. The trusted account, trusted UI and operator-controlled installation remain assumptions. Protection against a compromised UI, same-account malware, debugger access or deliberate credential extraction is not promised.

That limitation does not excuse ordinary agent self-reply through supported host APIs. The qualification threat case is an agent using its normal Shell/API tools and the host's ordinary configured service authentication, without extracting a separate operator secret or compromising the trusted UI. That agent must be unable to resolve Proceed requests. Capability negotiation, transport authentication and correct response correlation do not establish this separation.

## 1. Client-only interaction and independent operator authority

The OpenCode integration SHALL be a TUI-only plugin, loaded through the documented CLI plugin configuration, not a server decision RPC. Native MCP elicitation is not used for this decision path. Form `accept` means submission, not domain Approve or operator provenance. An ordinary form reply, service API user record or plugin RPC authenticated as the host client cannot grant Proceed decision authority.

Use local `ui.dialog.select` for Approve/Reject/Respond and `ui.dialog.prompt` for Respond text. Approve SHALL NOT be the initial highlighted option. Use `ui.dialog.show` when needed to display the complete question alongside local controls. Dismissal or `undefined` sends no decision. A local session panel can display pending questions independently in each session. Opening a panel or receiving a command dispatch never accepts a choice. Only completion of the local choice interaction may invoke the product decision client. Command arguments, server events and RPC inputs cannot supply or settle its answer.

The TUI SHALL connect directly to the broker, never through the OpenCode service for operator authorization. Its nonsecret configuration is exactly `state_dir`, `harness_id`, `owner_id`, `operator_key_file`. Both IDs match `[a-z0-9_-]{1,64}`. `owner_id` must name an existing configured principal, and `harness_id` names one operator-configured local OpenCode service installation. The first supported topology is local TUI, local OpenCode service and local broker on the same account/machine. Remote service/TUI operation is not qualified. A harness identity cannot silently be reused for another service installation.

The independent operator credential is `hop_` plus 64 random lowercase hexadecimal characters. `key_id` is the lowercase SHA-256 hexadecimal digest of the complete credential string. It is a public fingerprint and verifier, not sufficient authority by itself. Broker state stores only this verifier. The TUI alone loads the private file and keeps the credential in its process-local closure. It SHALL NOT use synchronized `storage.store`, host service storage, RPC, tool results, environment inherited by tools or model-visible arguments for it. No CLI command auto-loads an enrolled operator key to submit decisions or issue replacement authority. The owner's ordinary control/request credentials remain insufficient for decisions or enrollment acceptance.

`proceed-mcp harness keygen --operator-key-file <absolute-file>` SHALL create one new protected credential file containing exactly the credential plus LF. It takes no secret argument, refuses existing destinations and never reads, replaces or signs with an existing key. It neither enrolls a key nor approves work. Apply the startup dependency's protected credential-directory, current-account ownership, no-redirection, single-link, pre-write protection and exact-owned failure-cleanup rules. Keep this file outside repositories, broker state and MCP configuration. The TUI verifies those protections and actual file identity before loading. Its configuration carries only the path. No automatic import, secret export or credential-recovery command is added.

Successful key generation exits `0` and reports only the nonsecret destination and `key_id`. Invalid options or an existing destination exit `2`/`INVALID_ARGUMENT`. Unsafe or unverifiable protection exits `4`/`PROTECTION_UNVERIFIED`, and failed durable creation exits `4`/`STORAGE_FAILURE`. No success is reported before flush and final identity/protection checks. This design authorizes no access to existing operator, Telegram, control or owner credentials during development or qualification. Synthetic fixture authority is sufficient.

### Enrollment: authorization before the first decision

An explicit local UI setup action submits a proposed `(harness_id, owner_id, key_id)` enrollment. The UI displays that public fingerprint and the broker-issued enrollment ID. The paired human then sends `/harness <enrollment_id>` privately to the bot. The broker shows the proposed scope and fingerprint and asks explicitly whether to authorize that local operator key. The human must compare it with the genuine TUI setup display before confirming. A chat message, owner/control API call, synthetic user record or request capability alone cannot confirm enrollment.

This is a one-time delegation of decision authority, not a work approval and not an extra reviewer on subsequent requests. It does not prove or require that the local operator is the paired Telegram person. Another local operator can use the enrolled UI thereafter without contacting Telegram for each decision. The security cost is an additional protected local secret and explicit paired-chat confirmation during enrollment. Re-enrollment needs that confirmation again. This uses the existing paired-human setup authority rather than silently allowing agent self-enrollment or introducing cloud identity.

Enrollment is bound to the existing pairing identity and exact principal. The broker SHALL retain at most one pending enrollment per owner, for 300 seconds. Identical replay returns it without extending expiry. A different proposal receives `409`/`ENROLLMENT_BUSY`, never replacement. At most one active key is allowed per `(harness_id, owner_id)`. A different key receives `409`/`OPERATOR_ALREADY_ENROLLED` until the paired human explicitly revokes the old key using `/harness_revoke <key_id>`. Revocation removes decision authority, not retained outcomes or pending Telegram access. A consumed, rejected, expired or old-pairing confirmation cannot enroll anything. Enrollment messages and UI show fingerprints, never the credential.

Reuse the existing private-chat command and inline-callback transport. Enrollment Confirm/Deny callback data is respectively `he:<token>`/`hx:<token>`, where each token is 32 random lowercase hexadecimal characters mapped durably to that enrollment and its pairing snapshot. As with request callbacks, tokens correlate an interaction but confer no authority without the independently validated paired sender/private chat. Validate current pairing, enrollment scope, pending state and expiry atomically before accepting Confirm. Deny closes only that proposal. These callbacks cannot enter the request-resolution parser. Duplicate Telegram updates have no second enrollment effect. Revoke is accepted only from the current paired human/private chat and is idempotent. No control or owner HTTP endpoint can confirm, reactivate or replace a key.

### Reload and exit

Each plugin setup generation owns its transports, timers and dialog callbacks. Returned `Cleanup` fences that generation before aborting resources. Late dialog completions from it cannot submit. Reload may reread the protected file and use its still-enrolled key, but must refresh pending state and create fresh local dialogs for retained presentation bindings. Do not retain resolved dialog promises as permission. TUI exit loses local interaction state, not durable requests or enrollment. A genuinely new TUI may explicitly reopen the same session's pending question, without claiming that the old process resumed or redirecting an old waiting result.

## 2. Product-owned secure wire contract

All routes below use the merged startup contract's exact authenticated TLS-PSK origin `https://127.0.0.1:<configured-port>`. Read only the configured protected configuration and schema-2 `broker.lock` for port/instance trust, plus the explicitly configured operator key file. Do not load owner/control credentials or the Telegram token in the TUI. On every new connection, require the stable protected lock, TLS 1.2 only, sole cipher `PSK-AES256-GCM-SHA384`, fixed public selector `proceed-mcp-local-v1`, fresh PSK callback, no session reuse and no renegotiation. Require client `rejectUnauthorized:true`, `authorized:true`, no authorization error and the startup profile's PSK-only identity check. Recompare the complete protected lock after handshake before any HTTP bytes. Preserve the 1000 ms handshake ceiling within the exchange deadline. No HTTP downgrade, proxy, redirect, extra listener, host service password or request-capability substitution is permitted. Actual TUI runtime support for this transport is a qualification gate. Do not silently weaken it if the embedded runtime cannot support it.

The new `/v1/harness/` routes use `Authorization: Bearer <operator-credential>`. Their credential role is independent of existing owner/control routes. Enrollment alone permits an as-yet-unenrolled credential to propose its own verifier. Protected channel possession is not enrollment approval. Every other route requires an active enrolled verifier before any request disclosure or mutation. Browser `Origin` remains forbidden. JSON objects reject additional fields and retain the existing 64 KiB limit. IDs remain case-sensitive. Existing request IDs and timestamps retain their formats. `enrollment_id` is `hen_` plus 32 random lowercase hexadecimal characters and `presentation_id` is `hpr_` plus 32 random lowercase hexadecimal characters.

Preserve disjoint roles: owner credentials retain reservation/request/registration access, control retains pairing/status/shutdown, and both retain `GET /v1/ready`. Operator credentials gain only the harness routes, not readiness, startup, registration, request-capability access or shutdown. A valid existing credential used on the wrong role's route returns `403`/`FORBIDDEN`. Merely knowing a transport PSK, owner ID, session ID or public fingerprint grants none of these HTTP roles. Harness calls do not acquire or renew an adapter registration. The TUI observes a broker made available by normal MCP startup and never launches, stops, repairs or takes ownership of it.

| Route                                              | Exact input                                                                        | Successful result                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/harness/enrollments`                     | `{harness_id,owner_id}`                                                            | `202 {schema_version:1,enrollment_id,harness_id,owner_id,key_id,expires_at,state:"pending"}` for a new or identical pending proposal. Already enrolled matching scope returns `200` with the same fields and `enrollment_id:null,expires_at:null,state:"enrolled"`. No request details. |
| `POST /v1/harness/pending`                         | `{harness_id,owner_id,session_id}`                                                 | `200 {schema_version:1,presentation}`. `presentation` is null or the presentation below for this exact scope/session. Poll at most once per second per displayed session.                                                                                                               |
| `POST /v1/harness/presentations/{presentation_id}` | `{harness_id,owner_id,session_id,request_id}`                                      | `200 {schema_version:1,request_id,decision_id,resolution,response_text}` for this exact retained binding. Read-only authoritative observation, including pending or terminal status. `decision_id` is null while pending.                                                               |
| `POST /v1/harness/decisions`                       | `{harness_id,owner_id,session_id,request_id,presentation_id,choice,response_text}` | `200 {schema_version:1,accepted,request_id,decision_id,resolution,response_text}` after durable resolution. `accepted` is true only for this newly committed choice, false for an already terminal request.                                                                             |

`session_id` is a nonempty well-formed Unicode string encoded as at most 512 UTF-8 bytes, compared exactly without normalization. A presentation is exactly `{presentation_id,request_id,harness_id,owner_id,session_id,session_label,action,context,expires_at}`. These values come from the broker's immutable request, never from a UI-supplied question. Display the complete action, context, deadline, request ID and caller-supplied label before a choice. Render text inertly, not as terminal control sequences or executable links. A presentation ID is correlation, not a credential.

Extend the common request representation and its MCP structured/text projection with exactly `harness_channel:{state,reason}`. `state` is `unavailable`, `eligible` or `closed`. Pending requests are `eligible` only with an enabled route and active matching enrollment, with `reason:null`. Otherwise `reason` is `HOST_NOT_CONFIGURED`, `SESSION_ROUTE_UNAVAILABLE` or `OPERATOR_NOT_ENROLLED`, in that precedence. Terminal requests are `closed` with `reason:null`. This is eligibility/status, not proof of UI display, human receipt or call delivery. Instructions explain Telegram fallback and the corresponding setup/route repair. Existing fields and outcome semantics remain unchanged. No operator fingerprint, secret or presentation authority is added to model results.

`choice` is exactly `approve`, `reject` or `respond`. `response_text` is null for approve/reject and a well-formed Unicode string of 1-4096 scalar values for respond, matching the existing response limit and retained unchanged. Any other combination is `400`/`INVALID_ARGUMENT`, with no resolution. Refresh authoritative status after a transport error rather than claiming the choice failed to commit or automatically replaying it. Explicit retry of the identical bound choice is safe, returning the retained terminal resolution with `accepted:false` if already committed. The successful `resolution` is the existing terminal enum, and `response_text` reflects the recorded result, not necessarily the submitted losing choice.

Errors retain `{schema_version:1,error:{code,message,retryable}}`. Missing/malformed operator credentials or an unenrolled/revoked key on enrolled-only routes return `401`/`AUTH_REQUIRED`. Existing owner/control credentials never count as this role and receive the wrong-role refusal above. An active key attempting a foreign scope returns `403`/`FORBIDDEN`. Unknown/mismatched request or presentation returns `404`/`NOT_FOUND` without foreign details. Invalid payload is `400`/`INVALID_ARGUMENT`, unavailable pairing is `503`/`NOT_PAIRED`, storage failure is redacted `500`/`STORAGE_FAILURE`. These are operator HTTP errors, not additions to the MCP error catalog except `SESSION_BUSY` below. Enrollment conflicts are nonretryable until expiry or explicit operator repair. Authentication precedes scope/request lookup and deadline mutation. Preserve authenticated `503`/`BROKER_NOT_READY` admission while recovering/stopping and fence new harness mutations during drain. Legacy serving gains none of these routes.

Presentation IDs survive lost responses and broker restart and are never reassigned. Terminal presentation bindings remain retained with their request. On submission the broker checks the enrolled key, its scope and complete presentation binding inside the same serialized operation as deadline/resolution. Revocation racing a submission must therefore win before decision admission or lose to an already accepted decision. Merely loading a key before revocation is insufficient. A terminal matched request returns its unchanged outcome, including when another channel won. No actor, response body or status field can change the outcome type.

Each exchange has a 10000 ms absolute deadline including protected reads, TLS, headers and body, with abort on cleanup and a 64 KiB response ceiling. Late file-read completions cannot authorize another phase after cancellation/deadline. No new background supervisor or automatic mutation retry is added. Pending observation and harmless reenrollment observation may resume after a connection failure while the UI remains active. Stale UI closure is best effort, never the authorization boundary. Dialogs are actionable only before the immutable request deadline. At that deadline, session-panel disposal or plugin cleanup, fence their callbacks and release owned timers/transports. If the host cannot dismiss a dialog, its late result is inert rather than a retained permission.

## 3. Invocation and session binding

`mcp --owner <owner_id> --harness-id <harness_id>` opts this adapter principal into the configured host namespace. Omission retains Telegram-only behavior. An active matching enrollment is needed for presentation/decision access, not for portable waiting. Session metadata alone never grants this role.

For qualified host calls, read `CallToolRequest.params._meta["ai.opencode/sessionID"]` from transport metadata, not model arguments. Accept only the bounded session string above. Forward the configured harness ID and metadata value to the broker on preparation as optional local HTTP `harness_route:{harness_id,session_id}` in `POST /v1/handles`. The broker derives `owner_id` from the existing owner credential. No new model argument or decision tool is introduced. Persist the route with that reserved handle. Add the same optional `harness_route` to `POST /v1/requests` solely to check that the invoking context still matches the prepared route. It cannot retarget a handle. A supplied conflicting route returns `409`/`IDEMPOTENCY_CONFLICT`, without presentation or mutation. A missing route never substitutes the foreground session or changes the stored association.

Calls without safe metadata continue through the portable baseline without a harness presentation. If preparation had no route, later metadata cannot add one to that handle. The adapter omits the route when forwarding that creation and reports Telegram-only operation. If preparation had a route but the creating call has no safe metadata, retain the stored route for occupancy but do not expose a harness presentation until an authorized matching-context replay supplies it. Persist this presentation-enabled state. A known conflicting route is a conflict, never this missing-metadata fallback. Retain previously enabled routing on authorized replay or later metadata loss. The merged reservation body is `{session_label?}` and the creation body is `{request_handle,client_request_id,action,context,expires_in_seconds?}`. This change adds only optional `harness_route` to those bodies, preserving owner Bearer admission, `X-Proceed-Request-Capability` on creation, existing field validation and nondisclosing handle/capability denials. No route field is added to the five model-facing tool input schemas. The existing same-principal bearer-transfer model still permits authorized observation/cancellation and does not redirect an existing waiting result. Session routing is not nontransferable agent identity.

The merged one-live-adapter-per-owner registration lease remains 45000 ms with existing `OWNER_IN_USE` behavior. Distinct harness sessions multiplex through that adapter, not competing registrations for the same owner. Preserve original-call waiting, 32000 ms bounded wait exchanges, active-call reconnect and the separate 150000 ms startup availability budget. Harness UI polling or loss cannot extend any of these or the request deadline.

The TUI selects the session explicitly from `PanelInput.sessionID` or another documented session slot, verifies it with `data.session.get`, and queries only that exact scoped session. The callback captures the returned immutable presentation, not a reactive current-session reference. Tab switches, session titles, root/family membership and most-recent activity cannot retarget it. Unknown sessions show no decision UI. Separate session panels remain independently actionable even if modal dialogs display one at a time. Ordinary host APIs can expose/reroute labels or cause a prompt, but cannot supply the private operator credential or settle the client-local choice.

## Request and resolution invariants

The broker SHALL enforce these rules:

- Keep the existing two-tool prepare then create-and-wait workflow and private capability model. The same request ID, action, distinguishing context and absolute deadline appear on both surfaces. Neither surface contains request capabilities, operator credentials or transport secrets.
- Bind a harness-enabled request immutably to its protected transport principal, configured harness identity and opaque host session route. Route labels never grant request access or decision authority. A retained request capability continues to authorize explicit same-principal access, not human decisions or automatic session reattachment.
- In the broker's serialized durable creation operation, enforce at most one unresolved request per `(owner_id,harness_id,session_id)`. Reservation alone is not an unresolved request. Identical authorized replay preserves request identity, content and deadline. Changed payload retains the existing idempotency conflict. A different request in an occupied session returns HTTP `409` and MCP `isError:true` with `SESSION_BUSY`, message `Session already has an unresolved Proceed request`, `retryable:false`, before creating either actionable surface. Add that code to the adapter's closed error vocabulary. An explicit retry after the first request closes is allowed. Do not silently queue or discard either request.
- The session slot survives form dismissal, wait loss, adapter loss and broker restart. Release it only on committed resolution, explicit capability-authorized cancellation or expiry. Distinct sessions have distinct slots and may resolve in reverse order without a global interaction queue. UI presentation serialization must not serialize their broker admission or decisions.
- Both surfaces enter the same broker resolution operation. Authenticate the channel-specific authority and exact request binding before reading or changing its state. Inside serialization, recheck actionable status and `now < expires_at`, validate the domain choice, then durably commit exactly one resolution. Expiry, cancellation and competing choices use that same single-winner boundary.
- Approve, Reject and Respond are distinct domain choices. Respond requires validated text under the existing response limits and retains that text unchanged. It always resolves as instructions, including text such as "approved". No missing choice, default selection, error, silence or accepted form implies approval.
- Each presentation remains bound to its immutable request, not to the session's currently pending request. A late choice from an old prompt cannot affect a subsequent request in that session. Replays and losing submissions observe the retained resolution without another decision effect.
- Best-effort close or mark the losing surface stale after closure. Failure to update it never reopens authority. Separate recorded outcome, presentation update, result returned and confirmed receipt. A UI acknowledgement is not confirmation of originating-call delivery.
- Continue returning accepted outcomes only through the existing original-call JSON-RPC response. Loss of that call preserves explicit capability-and-principal-authorized retrieval and durable retention. It does not authorize another session, an agent turn or exited-process recovery.

Persist enrollment ID/scope/fingerprint/expiry/state and confirming pairing identity, active/revoked key status, immutable handle route, presentation binding and accepted decision provenance `{channel:"harness",key_id,harness_id,owner_id,session_id,presentation_id}`. Existing Telegram decisions retain their existing provenance. Persist the same single resolution/decision ID, not a second channel-specific decision. No plaintext operator secret enters the journal. Reconstruct session occupancy from pending routed requests after expiry processing, not from active waiters or UI connections.

The new reader SHALL recover existing version-2 state without changing its semantics. Configuration schema 2, ownership schema 2, lifecycle version 1 and public representation schema 1 remain unchanged. The merged journal declares file format 2 and record schema 2, validates exact mutation fields and refuses version 1. Before committing the first harness record, establish journal file format and record schema 3 through a durable, failure-safe upgrade under exclusive broker ownership. Retain every existing record's meaning, decision, verifier and delivery evidence. A crash during upgrade must leave recoverable old state or complete new state, never two writable histories. Old records have no harness route and remain Telegram-only. Private event encoding and upgrade mechanics belong to implementation. Recovery must reject unknown mandatory records or unsupported versions, including existing version-1 refusals. A binary without version-3 support must refuse this history, never ignore enrollment/revocation or occupancy. No downgrade to an old broker or manual state editing is supported. A failed or uncertain durable append fences admission and never reports accepted enrollment or decision. Pre-upgrade failure preserves the existing portable history and reports harness setup unavailable, not complete.

## Portable behavior and setup

Telegram remains the portable baseline without a proprietary host API/password, session metadata or elicitation requirement. Clients lacking configured trust, supported interaction or safe session routing do not receive the enhanced interaction. Report the missing channel and supported next action without claiming dual-channel delivery. This fallback does not satisfy this change's harness-channel acceptance.

For an admitted mirrored request, dismissed/declined/cancelled UI, invalid answer, host transport failure and waiting-call loss leave the durable Telegram request pending until separately resolved, explicitly cancelled or expired. Cancelling an interaction is not `cancel_approval`. Restart does not restore ephemeral UI authority or claim recovery of an exited host. Telegram access and authorized retrieval remain available under existing rules.

Empty-state setup SHALL use existing `init`, `owner add`, token provisioning and `pair`, then create a separate operator key, configure the TUI-only integration and adapter harness ID, and explicitly confirm the matching enrollment through the paired chat. No recurring broker terminal or stored-data editing is acceptable. Enrollment can also add this channel to existing protected state without resetting history. No setup operation approves work or changes native permission rules. Versioned compatibility and setup documentation must explain the additional operator role, paired-chat enrollment, key revocation and same-account limitation.
