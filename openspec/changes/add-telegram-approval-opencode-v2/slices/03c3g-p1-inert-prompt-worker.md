## Exact implementation-owned binding

- Sole export `createPortablePromptWorker({broker,telegram,logger=()=>{},traffic=null}={})` returns `{start(),stop(),diagnostic(),get failed}`. No timing options, clock dependency, test exports or production imports from tests.
- Require broker functions `responseWork`, `prepareResponsePrompt`, `recordPromptSent`, `recordPromptFailed`, `telegram.sendMessage` and function logger. Missing dependencies throw worker-specific TypeErrors. Suggested messages: `a prompt worker needs a recovered portable broker`, `a prompt worker needs a Telegram client`, `a prompt worker needs a logger function`. Tests require TypeError, not exact prose.
- `start():void` is idempotent and initiates immediate work plus a fixed1000ms scan. One pass, coalesced rescan, sequential sends, at most one in-flight send per request. Timers are native primitives, controlled by native mocks in tests.
- Candidate shape is existing `responseWork().prompts:[{request_id,chat_id,request}]`. Consume ONLY each candidate's request ID. Before EVERY attempt call `prepareResponsePrompt({requestId}) -> Promise<null|{chat_id,request}>`. Null suppresses send. No worker time sampling for admission, own expiry, cursor writer or snapshot payload reuse.
- Release core serialization before send. Recheck stop/shared traffic after preparation and before transport. Exact payload `{chat_id,text:renderPortableReplyPrompt(request),reply_markup:{force_reply:true}}`, second argument `{signal}`. No parse_mode, inline keyboard, selective targeting, ReplyParameters or authority fields.
- Validate success as plain Message/plain chat, positive safe integer `message_id`, `date`, numeric positive safe integer `chat.id`, `chat.type==='private'`, `String(chat.id)===prepared.chat_id`. No coercion or result-derived chat authority.
- Valid result calls `recordPromptSent({requestId,chatId,messageId}) -> Promise<null|{sent,request}>`. Receipt must flush before installed completion. Valid late result MUST drain even after terminal resolution/stop, without reopening or changing outcome. Same-owned-prompt `{sent:false,request}` is a duplicate success, not new completion or retry.
- Tuple collision `recordPromptSent` returning null: proposed request-local `recordPromptFailed({requestId,errorCode:'invalid_response'})`, then block/report invalid diagnostic, no new class. This is an implementation choice for owner ratification, not a normative source amendment.
- Actual attempt failures call `recordPromptFailed({requestId,errorCode}) -> Promise<null|{request}>`, classes exactly `unavailable|rate_limited|rejected|invalid_response`. This core changes no resolution/ledger/Telegram presentation state/cursor. Do not manufacture failed-attempt receipts from scheduled/ineligible/aborted-no-result work.
- `TELEGRAM_UNAVAILABLE`/`TELEGRAM_TIMEOUT` -> unavailable, `TELEGRAM_RATE_LIMITED` -> rate_limited. Only these retry per request at1/2/4/8/16/repeated30 seconds, valid nonnegative integer `retryAfter` seconds is a floor. Scans cannot bypass waiting/blocked scopes. Siblings progress independently.
- `TELEGRAM_REJECTED` -> rejected, block only that request. `TOKEN_REJECTED` -> rejected and synchronously stop ALL shared Telegram workers BEFORE fallible logging, independently of receipt success. `CANCELLED` supplies no receipt/retry when no result. Unknown send exception stops worker as processing failure, no invented failure mutation. Actual core failure remains distinct storage/processing classification, not platform retry.
- Reuse accepted presentation lifecycle/fence pattern with `traffic.add(listener)` at construction and `traffic.remove(listener)` on stop. An already-stopped fence immediately notifies. Fence all admissions/timers and abort transport on stop. Return the SAME nonrejecting drain Promise for every stop, including stopped/failed workers. No late timer/new send. Do not close core/Journal or alter local readiness.
- `diagnostic()` is null or one canonical fixed string below, `failed` reflects diagnostic presence. Contain logger faults, never log exception text, arbitrary codes, platform descriptions, URLs, request data or secrets. Logging cannot prevent shared cessation/drain.
