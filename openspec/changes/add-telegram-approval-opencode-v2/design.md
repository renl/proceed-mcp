# Design

Define the installable waiting-call Telegram approval preview, durable caller authority, and safe distribution boundaries.

## Context

Parent: [proposal](proposal.md). Product authority: [Telegram](specs/telegram-approval/spec.md), [continuation](specs/opencode-session-continuation/spec.md), and [distribution](specs/npm-distribution/spec.md). Existing [external research](research.md) remains useful for unchanged Telegram/npm boundaries, not authority for the superseded OpenCode-only path. Production already exists but requires contract, task, and test correction before further production work.

This design follows the corrected active proposal/specs and project direction. It is not a compatibility, feature-verification, or release claim. The first live validation target is OpenCode V2 with GeneralDeepSeekFlash; no other harness-specific implementation or tested compatibility is asserted.

Standard MCP sources ground the baseline below. Events and automatic post-timeout continuation are unsupported and deferred outside preview acceptance. Direct OpenCode API/password integration is paused, not an optional fallback.

**Preview scope reconciliation, 2026-11-05.** The approved preview boundary supersedes the earlier mandatory enhanced-path completion and prepublication live-proof gates. The user selected manual npm publication and deferred unfinished collector/CLI/release-workflow publishing automation to follow-up. The first preview is now public, published before implementation merge. User-supplied live evidence reports pinned-public setup, pairing, five-tool discovery, Approve/Reject/exact Respond, two concurrent correctly correlated outcomes and five terminal acknowledgements, with no action execution. This is supplied manual first-use evidence, not independent full-release acceptance, general compatibility, timeout coverage or confirmed shutdown. Completed doctor diagnostics and delivery retry remain deferred features. Clean build/package installation, secret safety, truthful instructions and independent applicable integrated-candidate verification remain required. This change can land independently on `main` as an exposed preview, with no stacked parent or dependency on future continuation or publishing-automation work.

Earlier checkpoint-specific refusals and sequencing below retain their historical meaning only at those named checkpoints. They neither disable the now-implemented preview baseline nor impose obsolete Events/live prerequisites on completion. Preserve their evidence and failures. No automated live harness, Ctrl+Break listener or containment expansion is required or authorized by this correction. No live access, archive, merge or publication authority follows from this document.

## Goals / Non-Goals

**Goals:** Return the actual human outcome in the still-active MCP call, persist decisions independently of call lifetime, isolate parallel owners, distinguish recorded/returned/confirmed outcomes, and deliver an installable preview for subsequent manual testing.

**Non-Goals:** Execution enforcement, permission-rule modification, harness HTTP callbacks, automatic host discovery, remote broker hosting, and recovery of an exited harness process. No browser inbox or floating widget is included. Harness permissions and operator policy remain the execution-enforcement boundary.

## Decisions

### 1. One persistent broker, many short-lived MCP adapters

The npm package `@meshimize/proceed-mcp` shall expose the unchanged `proceed-mcp` executable. Package scope does not rename the executable or reserve the npm name. The preview contains the first two logical components below. The third records deferred intent, not a required shipped component:

| Component | Responsibility | Prohibited responsibility |
|---|---|---|
| Local broker | Durable state, pairing, Telegram polling, single-winner resolution, request-capability authorization and delivery ledger | Executing actions or calling a harness API |
| Stdio MCP adapter | Standard handshake/catalog, protected transport-principal binding, returning outcomes on originating calls | Holding Telegram credentials, treating a connection as an agent identity, trusting session labels as authentication |
| Experimental event adapter (deferred, not shipped) | Future source-grounded exact-owner notification and scoped retrieval | Inventing event wire names, broadcasting outcomes, proprietary HTTP fallback |

The broker shall run as an explicit foreground process under the operator's terminal or supervisor. MCP startup shall not spawn another poller. Stdio adapter shutdown, MCP cancellation, and execution timeout shall not stop the broker or close a committed request. One broker shall own one dedicated Telegram bot token and one state directory. Sharing that token with another poller or webhook is unsupported and shall produce a setup diagnostic, not automatic webhook removal.

The current manifest declares Node `>=24`. Existing offline evidence is Windows Node 24.22.2 only, not an owner-approved all-version or all-OS support claim. The public support floor remains an owner decision in section 8. The npm artifact shall contain its executable runtime files and required runtime dependencies. No compiler, native add-on installation, database service, or postinstall script shall be required on the user's machine. The single-writer journal below supplies transactions without a separate database service. Private implementation structure remains implementation-owned. Dependencies shall be pinned in the lockfile.

**Alternatives rejected:** per-session pollers compete for offsets; immediate receipts do not deliver waiting-call outcomes; generic notifications do not establish agent resumption; mandatory proprietary metadata/API access destroys the portable baseline.

### 2. Public CLI and secure configuration

All commands accept `--state-dir <directory>`; otherwise use `PROCEED_STATE_DIR`, then `<home>/.proceed-mcp`. This documented product directory is independent of the working repository. No command shall silently read or modify OpenCode's private service registration files.

| Command | Contract |
|---|---|
| `proceed-mcp init` | Create empty versioned configuration, protected state directory, and local control credential; refuse to overwrite existing state. Print missing prerequisites, not a success claim for pairing/integration. |
| `proceed-mcp owner add <owner_id> --label <label>` | With broker stopped, create an immutable transport principal and separate protected 256-bit random credential file for an MCP adapter connection. Duplicate IDs fail. One connection may carry calls from multiple agent sessions. |
| `proceed-mcp serve` | Open protected state, acquire exclusive ownership, recover journal, validate configuration, and run broker. Telegram token comes only from `PROCEED_TELEGRAM_BOT_TOKEN`. |
| `proceed-mcp pair` | Ask the running broker to issue a one-use pairing challenge. Print the code only to the invoking operator, never ordinary logs. Refuse when already paired. |
| `proceed-mcp mcp --owner <owner_id>` | Run stdio MCP for that operator-bound transport principal. Read only its owner credential; stdout contains only MCP messages, including the request capability issued by `prepare_approval`. |
| `proceed-mcp doctor` | Deferred, not implemented in this preview. Unknown-command failure is not diagnostic completion. It is not a setup or publication prerequisite. |
| `proceed-mcp status [--request <request_id>]` | Show resolution, Telegram presentation, delivery stage, last redacted error, and next action. |
| `proceed-mcp retry <request_id>` | Deferred delivery feature. Retain the existing safe unavailable response and exit `3`, with no scheduling, mutation or delivery claim. Never inject a prompt, select another session or reopen a request. |

CLI exits: `0` completed command, `2` invalid arguments/configuration, `3` unavailable prerequisite or blocked integration, `4` storage/integrity failure. `serve` readiness does not imply first-use or release verification. Diagnostics go to stderr. `status --json` retains `{schema_version:1, requests:[]}`. No doctor JSON/check schema or completed diagnostics is required or advertised in this preview.

**Local readiness without a Telegram token.** An absent or empty `PROCEED_TELEGRAM_BOT_TOKEN` shall not prevent protected local broker startup, recovery, registration, preparation or observation. `serve` remains running after local readiness; it shall make no Telegram calls and print once to stderr `proceed-mcp: Telegram unavailable: set PROCEED_TELEGRAM_BOT_TOKEN and restart serve; local broker only\n`. This is a setup diagnostic, not a new public error code or Telegram readiness claim. Storage, configuration and ownership failures retain their existing startup refusals. Existing pairing is retained; a paired request may be committed with Telegram presentation pending while transport is unavailable, never marked sent or delivered. After token configuration and restart, pending presentation is eligible for processing only if still unresolved/unexpired. With no pairing, creation is refused as specified below. Enabling tests need no real token; controlled Telegram tests supply their synthetic token through the same environment variable, not a production bypass.

**Pair command success.** After the running broker durably issues a challenge, `pair` exits `0` with exactly two stdout lines: `Pairing code: <code>\nExpires at: <expires_at>\n`, and empty stderr. `<code>` is 32 lowercase hexadecimal characters (128 random bits); `<expires_at>` is the broker-returned UTC RFC 3339 deadline, five minutes after challenge creation. Print neither a paired-success assertion nor a bot URL/identity guessed from configuration. This output is sensitive operator-only setup material, not ordinary logging. The documented next step is to open the configured bot privately, send `/start`, then `/pair <code>` before expiry. Challenge issuance is not proof that the human paired or that Telegram is available. The temporary unavailable checkpoint below remains in force until pairing implementation replaces it; its exit/output rules are unchanged meanwhile.

**Owner-add stopped-state prerequisite.** `owner add` shall establish that `broker.lock` is absent before any state mutation or credential creation. Any existing record blocks addition with exit `3`, including a stale, malformed, empty or unreadable record; PID liveness or independently reported broker stoppage shall not authorize mutation while the record exists. Failure to establish existence/absence because an ownership stat/access operation fails exits `4`; inability to read the contents of a record whose existence is established does not bypass the exit-`3` refusal. Both refusals shall preserve all existing state bytes (including ownership record, configuration, journal and credentials) and credential inventory unchanged; no credential shall be created. No deletion, force option or recovery procedure is authorized. This absence prerequisite is not proof of race-free exclusion between owner addition and concurrent broker startup; that concurrency proof remains required separately under section 4.

Corrected configuration shall contain `schema_version:2`, `telegram.token_env` (fixed value `PROCEED_TELEGRAM_BOT_TOKEN`), `broker.port` (default 43189), and `owners[]` entries `{owner_id,label}`. Owner IDs match `[a-z0-9_-]{1,64}`; labels contain 1–128 Unicode scalar values. Credential paths are derived from the protected owner record, not supplied by a tool. Owner records contain no harness URL, password, host version allowlist, or proprietary session ID.

The broker port shall be an integer `1`–`65535`. Its adapter destination is exactly `http://127.0.0.1:<configured-port>`; redirects, proxies, DNS substitution, automatic port selection, and remote addresses are prohibited. This is private product IPC, not a harness API or an MCP HTTP transport.

The adapter and broker run on the same machine; the paired human supervises remotely through Telegram. No public broker or harness listener is required. Future topologies require separate review.

The baseline shall support native shared/multiplexed stdio connections. Distinguish three identities: `owner_id` authenticates the adapter's transport principal to the broker; `(adapter registration, JSON-RPC request ID)` identifies an invocation and its response destination; an agent-session label is display context only. Neither connection identity nor an RPC ID authenticates the logical agent session behind it. No per-session launcher, connection-exclusive session wiring, proprietary metadata, host API or host calibration is a baseline prerequisite. No automatic exited-process reattachment is authorized.

The broker listener shall bind only `127.0.0.1`, require a 256-bit random Bearer credential on every route, reject browser `Origin` headers with `403`, provide no CORS allowance, and accept only JSON bodies up to 64 KiB. Separate control and per-owner credentials authorize control versus MCP routes. A per-owner credential cannot access another owner or pairing/retry controls; request routes additionally require the request capability defined below. Control, owner and registration credentials shall never enter model arguments/results or journal records. The separate request capability is intentionally issued through a tool result and supplied in subsequent tool arguments; persist only its verifier, never its plaintext. Redact all capabilities from logs, errors, status, Telegram, request representations and package files. Authentication failures return `401` with no request details.

The state directory and credential files shall be accessible only to the current OS account: owner-only permissions on POSIX and an owner-restricted ACL on Windows. Windows shall not be treated as protected merely because a POSIX mode was requested. If protection cannot be established or verified, setup/start shall fail with an actionable diagnostic. The local account and operator-controlled client wiring are trusted; this product does not sandbox malicious same-account processes or credential theft. Pairing and reply text are sensitive local data even though they are not credentials.

**Request-owned authorization:** The broker shall issue an independent, unguessable 256-bit bearer capability for each prepared handle through `prepare_approval`'s original RPC response. Possession, together with the transport principal, authorizes that handle/request only. Request IDs, `client_request_id`, labels, `clientInfo` and proprietary `_meta` confer no authority. One live adapter registration per owner remains enforced (`OWNER_IN_USE`); it limits registrations, not agent sessions or simultaneous unrelated calls.

The trusted harness must route each RPC result only to its invoking context and keep capabilities out of unrelated contexts. The product does not authenticate a nontransferable agent-session identity or protect against a harness that shares all contexts, a caller deliberately disclosing its capability, or a malicious same-account process. Equal labels and knowledge of another request ID still grant no access. If product ownership is intended to deny even a caller holding a deliberately transferred valid capability, that stronger session-specific control is impossible over an indistinguishable shared principal without additional authenticated host support; it requires a targeted product-security decision, not a mandatory portable-core prerequisite.

**A1b diagnostic and observation scope.** The tokenless diagnostic above belongs to the first runtime/scheduling cut, not C. Emit it only after successful local startup, once per `serve` process; failed startup prints neither readiness nor this post-readiness diagnostic. Token presence proves no Telegram availability: before C there is no implemented Telegram transport, pairing or presentation claim, even with a configured token. Do not add a guessed transport-ready diagnostic. Human `status` shall use `owner_id` and display-only `session_label`, never legacy `origin_id`/`session_id`; show resolution, Telegram state, delivery state, deadline, any redacted delivery error and next action. Pending unsent work must not imply human receipt; expired work must identify a non-approval closure requiring a new request if approval is still needed. JSON status retains its existing shape. HTTP `500` / `STORAGE_FAILURE` from status yields CLI exit `4`, empty stdout and a redacted storage diagnostic, never an empty successful list or prerequisite exit `3`.

### 3. MCP and local cross-component contracts

The MCP adapter shall implement the classic initialize handshake for revision `2025-11-25`, advertise tools, and expose the tools below. Respect negotiated capabilities; no Events, tasks, sampling, resources, or proprietary metadata are baseline prerequisites. Inputs are objects with no additional properties. Identifiers are case-sensitive; times are UTC RFC 3339 strings. This protocol target is not a claim that all MCP clients are tested.

| Tool | Arguments | Effect |
|---|---|---|
| `prepare_approval` | Optional `session_label` (1–128 Unicode scalar values, display only) | Return `{schema_version:1,request_handle,request_id,request_capability}` on this call only. Reserve durable request identity and authority; do not create an actionable approval or send Telegram. |
| `request_approval` | Required `request_handle`, `request_capability`, `client_request_id` (1–128 ASCII letters/digits/`_-`), `action` (1–1000 Unicode scalar values), `context` (0–1000); optional `expires_in_seconds` integer 60–86400, default 3600 | Authenticate the handle, durably create/reuse its request and keep this call waiting until human resolution, expiry, or explicit product cancellation; return the actual outcome, not merely a receipt. |
| `get_approval` | Required `request_id`, `request_capability` | Read only the capability-authorized request, applying expiry first. No delivery side effect. |
| `cancel_approval` | Required `request_id`, `request_capability` | Resolve only the capability-authorized pending request as cancelled; return an existing terminal outcome unchanged if already resolved. |
| `acknowledge_approval` | Required `request_id`, `request_capability`, `decision_id` | Record that a capability holder received the matching terminal outcome; idempotent, no new decision or continuation. |

The broker derives `owner_id` from the authenticated adapter credential, never from a model argument or session metadata. Each in-flight wait is correlated by `(adapter registration, JSON-RPC request ID)` and may respond only on that original stdio call, using the identical JSON-RPC ID. No outcome or capability is broadcast. The trusted client owns subsequent dispatch to the invoking agent context; the server shall not claim it authenticated that context. Registration is ephemeral; principal identity and capability verifiers persist across broker restart. Adapter exit ends its calls' reachability, not the requests' lifetime. A retained capability permits later explicit observation on the same principal, not automatic session reattachment or a new agent turn.

Allocate `request_handle = hdl_` plus 32 random lowercase hexadecimal characters, reserved `request_id = req_` plus 32 independently random lowercase hexadecimal characters, and `request_capability = cap_` plus 64 random lowercase hexadecimal characters. Commit `{owner_id,request_handle,request_id,capability_hash,session_label,prepared_at}` before issuing the capability; the hash is SHA-256 of the complete capability string. Handles and reserved request IDs are unique, immutable and never reassigned. A lost preparation result has no actionable request and grants no fallback retrieval; retry preparation allocates fresh authority, not a replay of the secret. Unused handles remain in protected state; automatic history deletion remains deferred. Read/cancel/ack of a reservation with no committed approval returns `NOT_FOUND`, with no side effect. Returning the reserved request ID before waiting allows a retained capability holder to retrieve or cancel after actual request creation even if the waiting result is lost.

The idempotency key is `(owner_id,request_handle)`, authenticated by its capability, not a model-chosen collision domain. Create at most one approval under its reserved request ID. Changed `client_request_id`, action, context or effective expiry duration yields `IDEMPOTENCY_CONFLICT`; replay never extends the deadline. Equal `client_request_id` values on different handles shall create independent requests. An authorized identical retry attaches to the same request; only one active waiter per request is permitted (`WAIT_ALREADY_ACTIVE` otherwise). Length checks include complete Telegram rendering; reject over-limit input before request persistence.

**Compatibility tradeoff:** Setup of each approval requires two ordinary `tools/call` invocations: prepare authority, then create-and-wait. This is a project-defined tool workflow, not a new MCP protocol feature. The first result is only an authority reservation, never an approval receipt or human outcome. Returning a capability only with the terminal outcome would be too late for pending cancellation or lost-result recovery. Do not substitute invented intermediate notifications. Tool instructions shall require private capability retention with the handle/ID and prohibit echoing it in assistant acknowledgements. The proposal/specs approve this workflow and same-principal bearer transfer, not nontransferable authenticated-session identity. Supplied manual first-use evidence covers preparation and waiting-call outcomes with acknowledgements. Live retention across timeout remains unverified, not a prepublication gate.

Tool success shall contain matching JSON in `structuredContent` and a text content block, with `isError:false`. The common request representation is:

| Field | Type / meaning |
|---|---|
| `schema_version`, `request_handle`, `request_id`, `client_request_id` | `1`, stable IDs; none is an authorization secret |
| `owner_id`, `session_label` | Immutable transport principal and prepared caller label (default operator label); label is display only, not a verified session identity |
| `action`, `context`, `created_at`, `expires_at` | Immutable request and deadline |
| `resolution` | `pending|approved|rejected|responded|expired|cancelled` |
| `resolved_at`, `response_text` | Nullable; text non-null only for `responded` |
| `decision_id` | Null while pending; `dec_` plus 32 random lowercase hexadecimal characters allocated once at terminal resolution, including non-approval closures |
| `telegram_state` | `pending|sent|failed` |
| `delivery_state` | `not_applicable|pending|returned|confirmed|unavailable|blocked`; section 6 defines meanings |
| `delivery_error` | Null or `{code,message,retryable}`; redacted current delivery diagnostic, not an append-only error history; section 6 defines clearing on receipt/write evidence |
| `event_capability` | `{status,revision,reason}`; status `unverified|unsupported|verified`, revision nullable pinned contract identity, reason nullable redacted diagnostic. Baseline initial value is exactly `{status:"unverified",revision:null,reason:"No verified Events contract or host support"}`. Only demonstrated absence/incompatibility permits `unsupported`; neither status enables events. Research commit pins are not admitted revision values. |

**Response fields and authority privacy.** Broker producers shall emit only the common request representation above. When admitting a broker request representation, the adapter shall validate its documented fields and invariants, then expose only those fields in both MCP result channels; for `delivery_error` and `event_capability`, expose only their documented members. Unknown fields are not an extension of schema version 1: omit them without rejecting an otherwise valid representation or assigning them authority. Presence of a top-level `request_capability` or `registration_secret` is instead a malformed authority disclosure: reject the reply as redacted `BROKER_UNAVAILABLE`, `retryable:true`, without echoing its contents. This rejection applies even when the field is null or malformed; it is not a search for credential-like substrings. Other unknown fields cannot leak through because they are omitted, not because a credential-name denylist is exhaustive. Preparation and registration retain their separate authority-issuing response contracts.

Preserve accepted `action`, `context` and `response_text` exactly. A caller or human may quote a field name or a capability-looking string in those text values; resemblance alone shall cause neither rejection nor redaction. This is the existing deliberate-disclosure trust boundary, not permission to add authority fields. Response projection tolerates additive broker metadata without forwarding it; it does not waive required-field, outcome or privacy validation, authorize new public response fields, or change request authorization. This clarifies the common representation and existing privacy boundary; it does not establish a new security posture or a broader validation gate.

`request_approval` returns the terminal representation as its actual tool result after durable resolution. `get_approval` may return pending or terminal state, including after timeout, but never triggers a turn. MCP instructions shall require acknowledgement of a received terminal `decision_id`, acknowledgement of the matching request/outcome in the subsequent assistant turn, and deduplication by `(request_id,decision_id)` before acting. Pending, expiry, cancellation, rejection, and errors grant no approval; Respond is instructions only, including approval-like words. Actions still needing approval require a new explicit request. Retrieving/acknowledging the same outcome is observation, not a new decision effect.

`notifications/cancelled` stops only the identified MCP invocation/wait, normally without a response. Execution timeout, EOF, adapter termination, and cancelled invocation do not cancel/expire the durable approval. Only capability-authorized `cancel_approval` or the disclosed deadline closes a pending approval. Do not infer business cancellation from free-text protocol cancellation reasons. A lost call cannot receive a result; retain the decision for capability-authorized retrieval and separately report event capability. If the caller lost its capability, a request ID or label cannot recover it; report delivery unavailable rather than grant access. No progress notification shall promise unlimited timeout extension. Broker disconnect during a live wait shall trigger authenticated reconnection by the same retained adapter at 1, 2, 4, 8, 16, then 30-second intervals, while that invocation remains active; never recreate its request or transfer its waiter to another call/session.

**Live-wait reconnect scope.** The ladder above means delays of 1, 2, 4, 8, 16, then repeated 30 seconds between failed transport attempts, with no fixed attempt-count cutoff while the original invocation remains active. This is continuation of that invocation's wait only, not an open-ended background retry service or a promise to extend the client's timeout. Every exchange, timeout and backoff shall be abortable by that invocation's cancellation and by adapter close/EOF; after either, no reconnect may start and no late completion may write its result. Reconnect retains the request identity/capability and original response destination; it shall not replay creation or another business mutation, resume an exited call, or attach another invocation. Ordinary registration and non-wait operations retain the finite attempt rule below. Re-establish lost registration only through its existing authenticated single-flight lifecycle; preserve heartbeat, lease and captured-incarnation fencing. Never delete a registration to make room, guess lost authority, or bypass `OWNER_IN_USE`.

Tool execution errors shall use `isError:true` and structured/text `{schema_version:1,error:{code,message,retryable}}`. Codes: `INVALID_ARGUMENT`, `NOT_PAIRED`, `BROKER_UNAVAILABLE`, `AUTH_REQUIRED`, `FORBIDDEN`, `OWNER_IN_USE`, `WAIT_ALREADY_ACTIVE`, `IDEMPOTENCY_CONFLICT`, `DECISION_MISMATCH`, `NOT_FOUND`, `ENHANCEMENT_UNAVAILABLE`, `STORAGE_FAILURE`, `UNSUPPORTED_SCHEMA`. Unowned IDs yield `NOT_FOUND` without existence disclosure. Missing owner configuration prevents adapter startup. Unknown tools/malformed MCP messages use JSON-RPC protocol errors; timeout is not a human outcome.

This tool-code list is closed. Propagate a broker error only when its versioned envelope has a recognized code, string message and boolean `retryable`; preserve those values. Transport abort/closure, unreadable or malformed broker replies and unrecognized error codes shall map to redacted `BROKER_UNAVAILABLE` with `retryable:true`, not `BROKER_REJECTED` or a private local-client code. Retrying requires a still-open adapter and the existing operation's authority/idempotency rules; the error does not authorize automatic replay or prove that a mutation did not commit. At EOF no tool response to the closed input is required, and no response-write drain may delay shutdown beyond the budget below.

The broker's authenticated HTTP API is product-defined, not an invented OpenCode API:

| Route | Credential / body | Success |
|---|---|---|
| `POST /v1/adapter` | Owner credential; `{}` | `201 {registration_id,registration_secret}`; random ephemeral registration, one live adapter per owner |
| `DELETE /v1/adapter/{registration_id}` | Same owner credential and registration secret | `204`; release only this registration, never close approvals |
| `POST /v1/handles` | Owner credential; `{session_label?}` | `201 {schema_version:1,request_handle,request_id,request_capability}`; durable reservation, no Telegram effect |
| `POST /v1/requests` | Owner credential and request capability; `{request_handle,client_request_id,action,context,expires_in_seconds}` | `201` new / `200` identical replay, request representation; this internal receipt is not the MCP result |
| `GET /v1/requests/{request_id}` | Owner credential and request capability | `200` authorized request, expiry applied first |
| `POST /v1/requests/{request_id}/wait` | Owner credential, request capability and registration secret; `{registration_id}` | Wait up to 25 seconds; `200` terminal request / `204` still pending; adapter repeats while original MCP invocation lives |
| `POST /v1/requests/{request_id}/cancel` | Owner credential and request capability; `{}` | `200` single-winner request |
| `POST /v1/requests/{request_id}/acknowledge` | Owner credential and request capability; `{decision_id}` | `200` matching request with durable confirmed status |
| `POST /v1/requests/{request_id}/returned` | Owner credential, request capability and registration secret; `{registration_id,decision_id}` | `200` request; idempotently record adapter-reported successful result write, never downgrade confirmed |
| `POST /v1/pairing` | Control credential; `{}` | `201` `{code,expires_at}` |
| `GET /v1/status` | Control credential | `200` status JSON |
| `POST /v1/requests/{request_id}/retry` | Control credential; `{}` | `200` request if no work needed; `503` enhanced path unavailable; future scheduling requires the verified section 6 contract |

HTTP errors use the tool error envelope: `400` invalid arguments, `401` authentication, `403` forbidden control/browser access, `404` unowned/unknown request, `409` idempotency/registration/wait/decision conflict or already paired, `503` missing prerequisite or unavailable broker/enhancement, `500` storage failure. No HTTP endpoint shall approve, reject, or supply response text. Control credentials authorize operator setup/status/retry, not a substitute decision API. These routes are production adapter/broker contracts, not test-control APIs.

**Creation pairing prerequisite.** `POST /v1/requests` shall enforce browser/readiness, Bearer/owner role, JSON limits/field validation, and matching handle capability before testing pairing. For valid authorized input with no pairing, return HTTP `503` and exactly `{schema_version:1,error:{code:"NOT_PAIRED",message:"No human is paired; run proceed-mcp pair and complete private-chat pairing",retryable:false}}`. Repeating unchanged setup cannot fix this; after pairing, the caller may explicitly retry using the same reserved authority. Refusal shall leave journal bytes/sequence, reservation, request inventory, decisions and presentation work unchanged; allocate no approval, deadline, callback token or waiter. Preparation itself remains permitted before pairing. Do not disclose this prerequisite instead of an authority failure. Creation snapshots the paired user/chat in its transaction; pairing is not inferred from a token, fixture transport, registration or label. Identical creation replay, authorized reads and control status apply due expiry before returning; authority-denied operations never trigger expiry mutation.

**Temporary setup checkpoint — 03A.1b-ii-c only.** Before Telegram pairing and request lookup/delivery operations are implemented, the following diagnostic contract applies on the unpromoted, incomplete change branch. It does not replace the eventual route/CLI behavior above or satisfy pairing, request lookup, waiting-call or enhanced-delivery acceptance.

| Correct-control request with valid JSON `{}` | HTTP status | `error.code` | Exact `error.message` | `error.retryable` |
|---|---|---|---|---|
| `POST /v1/pairing` | `503` | `ENHANCEMENT_UNAVAILABLE` | `pairing is not implemented in this setup checkpoint` | `false` |
| `POST /v1/requests/{request_id}/retry` | `503` | `ENHANCEMENT_UNAVAILABLE` | `request retry is not implemented in this setup checkpoint` | `false` |

Each response shall contain exactly `{schema_version:1,error:{code,message,retryable}}` with the row's values, using the existing common error envelope. `retryable:false` means repeating the command cannot enable an operation absent from this checkpoint; it is not a permanent product-support verdict. Retry shall report this unavailable result before request lookup, including for an unknown request ID; do not fabricate a request, return lookup-derived `404`, or claim scheduling/delivery. Neither operation shall create a challenge, pairing, request, decision or delivery intent, or mutate the journal. Existing input limits and validation remain in force.

Authentication/role checks precede these unavailable outcomes: missing/invalid Bearer authority returns `401` / `AUTH_REQUIRED`; a valid owner credential on either control route returns `403` / `FORBIDDEN`, never `503`. Browser `Origin` remains forbidden under the existing boundary. No request details or secrets may enter any diagnostic. No new route, recovery/reset option or weaker authentication is authorized.

For this checkpoint, `pair` and `retry <request_id>` shall propagate the corresponding unavailable classification as CLI exit `3`, with empty stdout and exactly `proceed-mcp: <error.message>\n` on stderr, using the message above. No pairing-code or scheduled-delivery output is permitted. Argument/configuration, transport and storage failures retain their existing classifications; this mapping applies when the unavailable operation is reached.

**Checkpoint status shape.** Correct-control `GET /v1/status` shall return `200` with exactly `{schema_version:1,broker:{pid,port,started_at},requests:[]}`. `pid` is the running broker's actual integer process ID; `port` is its configured, bound loopback port. `started_at` is the UTC RFC 3339 timestamp captured when that broker authority instance is initialized, fixed for its lifetime and recaptured on restart, not a status-query timestamp or fabricated readiness proof. Durable handle reservations are not approval requests and shall not populate `requests`. Successful unfiltered `status --json` shall exit `0` and print only `{schema_version:1,requests:[]}` as JSON plus a terminating newline; it shall not add the HTTP `broker` object or imply pairing/delivery success. JSON whitespace is not significant.

The adapter shall pass the request capability in `X-Proceed-Request-Capability` on every handle-bound creation and request route above, not in the URL or ordinary body. The broker shall validate its verifier, immutable principal and handle/request binding before reading state or applying expiry/cancellation/acknowledgement. Missing, invalid, foreign or mismatched capabilities yield `404` / `NOT_FOUND` without existence disclosure; malformed tool input remains `INVALID_ARGUMENT`. A valid transport credential alone shall not authorize those routes. The operator control plane remains trusted for local status; MCP exposes no request-listing or capability-recovery tool.

#### A1b public create/read binding

For these recognized routes the precedence is browser denial, existing listener-startup readiness gate, Bearer authentication, owner role, then route input and request authority. Invalid/missing Bearer returns `401` / `AUTH_REQUIRED`; a control credential returns `403` / `FORBIDDEN`.

Creation parses at most 64 KiB as an object and rejects additional properties with `400` / `INVALID_ARGUMENT`. Its only allowed fields are `request_handle`, `client_request_id`, `action`, `context`, `expires_in_seconds`; duration alone is optional and defaults to `3600`. This makes explicit the existing public no-additional-properties rule; private ignored extras grant no public permission. Validate client key/action/context/duration before capability binding. Missing/malformed/foreign/unknown handle or header capability then returns `404` / `NOT_FOUND`, not pairing information. Bind `X-Proceed-Request-Capability` to the exact handle and credential-derived owner; accept no body capability or caller-supplied owner/label/state. After authority, retain section 4's serialized conflict-before-expiry, identical-replay expiry and first-creation pairing rules. Return only the common request representation: `201` for this call's flushed new creation, `200` for identical replay; private null maps to `404`, never success.

Missing or invalid required caller payload (`client_request_id`, `action`, `context`) and invalid supplied duration are `400` / `INVALID_ARGUMENT`. Missing or malformed `request_handle` is instead an authority-binding failure under the `404` rule above, after caller-payload validation; a generic required-field or handle-pattern check shall not reclassify it as `400`. This HTTP distinction does not change malformed MCP tool arguments' `INVALID_ARGUMENT` classification.

Read requires the owner Bearer and `X-Proceed-Request-Capability` bound to the exact path request ID. It has no JSON body requirement; introduce no GET body schema. Missing/malformed/unknown/foreign/mismatched request authority and an unused reservation return `404` / `NOT_FOUND`. Only an authorized actual request enters target expiry; never sweep globally on a denied read. Neither create nor read requires `X-Proceed-Registration` or a live registration at the HTTP boundary. An irrelevant registration header grants no authority and shall not become an admission requirement. Existing HTTP storage redaction remains in force.

Enabling GET intentionally enables the existing MCP `get_approval` forwarding path to return pending/expired requests before B. This is approved scoped observation, not a waiting result, delivery report, acknowledgement or agent resumption. Preserve the adapter's lazy registration gate and same-principal capability-transfer behavior; include newly reachable MCP success/error behavior in the public-route cut's affected checks. `request_approval` remains explicitly unavailable until B. Wait/returned/cancel/acknowledge gain no success path in A1b; valid authority on an actionable request must not manufacture their outcomes or delivery evidence. Their enabling contracts remain A2/B.

**A1b catalog and instructions fidelity.** With public read enabled, initialize instructions and tool descriptions shall distinguish authorized `get_approval` observation of actual pending/expired requests from `NOT_FOUND` for unused reservations or denied authority; they shall not describe all retrieval as reserved-only denial. They shall retain private capability/identity retention, terminal acknowledgement, assistant outcome acknowledgement and stable-decision deduplication guidance from this section, while explicitly stating that `acknowledge_approval` is unavailable at this checkpoint and cannot record receipt yet. Cancellation remains unavailable here, and `request_approval` remains explicitly unavailable. Acknowledgement availability shall not be tied to waiting implementation: A2 owns its enabling contract. The interim disclosure neither waives the final acknowledgement requirement nor permits retrieval or an unsuccessful acknowledgement to mark delivery returned/confirmed. Exact source strings remain an implementation choice within these meanings; no waiting, approval, Telegram presentation or agent-resumption success is implied.

#### A2b acknowledgement and returned HTTP binding

Both routes retain browser/readiness, Bearer and owner-role precedence above. Parse at most 64 KiB into a JSON object before further checks. Acknowledgement accepts exactly `{decision_id}`; returned accepts exactly `{registration_id,decision_id}`. Reject additional fields and invalid decision IDs with HTTP `400` / `INVALID_ARGUMENT`; `decision_id` must be a raw string matching `dec_` plus 32 lowercase hexadecimal characters, without coercion. For returned, authenticate the supplied registration ID and `X-Proceed-Registration` secret against the credential-derived owner and current unexpired registration **before** validating remaining fields (including additional fields and `decision_id`), as required by the registration order below. An invalid registration therefore retains its exact HTTP `401` envelope even when those remaining fields are invalid.

Next bind the path request ID and `X-Proceed-Request-Capability` to the owner and actual request. Missing/malformed/unknown/foreign/mismatched request authority or an unused reservation yields HTTP `404` / `NOT_FOUND`. Acknowledgement requires no registration; an irrelevant registration header shall not become a prerequisite. Inside serialization, an authorized pending request or a different well-formed decision ID yields HTTP `409` / `DECISION_MISMATCH`, `retryable:false`, without time sampling, expiry, identity allocation or append. These evidence operations do not resolve a pending request, even if its deadline is due; the existing scheduler/read/cancel paths own expiry.

For a matching terminal decision, apply section 6's first-evidence/idempotency rules through the exact journal mutations in section 4. Return HTTP `200` with only the independent common request representation after successful flush/install, or without append for an already-recorded matching evidence kind. Do not expose private evidence timestamps or add fields to that representation. Returned renews the authenticated registration lease only after the whole operation succeeds, including an idempotent success; parse/authentication/authority/conflict/storage failures do not renew it. Renewal cannot revive an expired registration or renew a replacement incarnation; a committed evidence record is not rolled back if its registration expires during flush. Existing storage fences, runtime-failure refusals and redaction remain applicable; a failed/uncertain append is never a successful evidence response.

#### Registration timing and authority

Initialize, catalog discovery and catalog-only unavailable calls shall not contact the broker or register. In a broker-bound adapter, the first implemented tool execution with valid tool arguments shall ensure registration before forwarding its operation, including preparation and reserved management. Concurrent executions share one in-flight registration attempt; after it succeeds, unrelated operations remain concurrent. Invalid tool arguments retain `INVALID_ARGUMENT` without registration. A duplicate live owner returns HTTP `409` / `OWNER_IN_USE`, propagated as a tool execution error without forwarding or mutation; it is not a startup/catalog failure. Unimplemented `request_approval` remains explicitly unavailable in the reservation checkpoint.

This adapter lifecycle gate does not change HTTP request authority: `POST /v1/handles` remains owner-only, and reserved read/cancel/ack retain their owner-plus-request-capability checks without a registration requirement. Registration neither authenticates an agent session nor replaces a request capability. Same-principal capability transfer remains authorized. U1's verified registration-free execution is an enabling predecessor, not proof of the later lifecycle gate; affected public execution tests shall be rerun when binding is added.

#### Registration authentication and lease

Registrations contain a random ephemeral ID and protected random 256-bit secret, returned only by `POST /v1/adapter`. Keep both in memory; never journal registrations or expose their secrets to the model. The journal remains version 2 with no registration-related format change. Registration IDs need no new public encoding. Wait, returned, heartbeat and registration-delete requests carry the secret as `X-Proceed-Registration`, alongside the owner Bearer credential. Add `POST /v1/adapter/{registration_id}/heartbeat` with JSON `{}`, success `204`.

The adapter shall accept registration-create success only as HTTP `201` with an object containing valid `registration_id` and `registration_secret` under the broker's existing encodings (`reg_` plus 32 lowercase hexadecimal characters, and 64 lowercase hexadecimal characters respectively). Any other success status or malformed authority fails closed as `BROKER_UNAVAILABLE`: do not forward the business operation, install the binding, start a heartbeat or release using guessed authority. This validates the existing broker encoding, not a new ID format or recovery route.

For recognized registration routes and registration-bound operations, validation order shall be:

1. Existing browser denial and broker-readiness checks; Bearer authentication (`401` / `AUTH_REQUIRED`), then owner-role check (control credentials yield `403` / `FORBIDDEN`).
2. For JSON-bearing routes, enforce the 64 KiB limit and parse a JSON object (`400` / `INVALID_ARGUMENT` on failure), before registration lookup. Delete has no JSON body requirement.
3. For operations requiring an existing registration (not registration-create), authenticate the registration ID, secret, credential-derived owner and unexpired lease together. Missing/malformed ID in an otherwise recognized operation, missing/malformed/wrong secret, unknown/foreign/expired registration all yield exactly `{schema_version:1,error:{code:"AUTH_REQUIRED",message:"registration authentication required",retryable:false}}`, HTTP `401`. No existence details, renewal or other effects are permitted. A missing path segment that does not match a route remains route-not-found, not a new route.
4. Validate remaining body fields, then request capability and business preconditions where applicable. Registration-create and heartbeat bodies shall contain no fields; create checks its valid body before duplicate-owner admission. Valid registration authentication does not bypass request authority. Existing non-registration routes retain their validation order.

Heartbeat is sent every 10 seconds after registration, even without waits. The lease expires when `now >= last_authenticated_activity + 45 seconds`. Only successful, fully validated registration-bound activity renews it (heartbeat, wait or returned); owner-only handles/management calls and failed requests do not. Delete releases it rather than renewing it. Expiry shall be checked before authentication and duplicate-owner admission, without requiring a sweep timer. Expired/stale operations cannot renew or delete a replacement registration. Registration expiry is reachability loss, never approval cancellation, capability recovery or waiter transfer. Each original MCP waiter remains reserved across all 25-second internal wait turnovers; overlapping same-request calls remain rejected, not unrelated approvals on a shared connection.

#### Wait admission, settlement and detachment

`POST /v1/requests/{request_id}/wait` accepts exactly `{registration_id}`. Apply the registration-bound validation order above: parse/limit the JSON object, authenticate the registration, reject additional fields, then bind the path request and header capability to the credential-derived owner and an actual request. Registration denial retains the exact HTTP `401` envelope above; missing/foreign/mismatched request authority or an unused reservation retains HTTP `404` / `NOT_FOUND`. Neither denial may disclose waiter presence, sample request-deadline time, apply expiry or allocate a waiter. After authority and existing storage/runtime-health checks, serialize admission with resolution and other wait admissions; a second active waiter for that request yields HTTP `409` / `WAIT_ALREADY_ACTIVE`, `retryable:false`, without deadline processing or renewal. Registration authority never replaces request authority.

**Duplicate-wait fail-closed decision.** A valid recognized HTTP `409` / `WAIT_ALREADY_ACTIVE` envelope shall always propagate as the corresponding `isError:true` tool error with its broker message and `retryable:false`, including on re-admission after transport loss. It is not a transient transport failure and shall not enter the reconnect ladder. End that invocation's wait and release only its locally owned resources; retain the durable request/outcome for capability-authorized observation. Do not infer that a surviving broker exchange belongs to this invocation, poll through the conflict, transfer its waiter, or delete/re-register to evade it. A locally detected overlapping same-request invocation likewise receives `WAIT_ALREADY_ACTIVE`, `retryable:false`, without disturbing the original invocation. Transport loss alone permits the scoped reconnect above; an explicit conflict supplies no identity-transfer authority.

**G1 — settled-success renewal.** Admission alone shall not renew the registration. Renew only when a fully validated wait settles successfully as HTTP `200` terminal or HTTP `204` still pending, including an immediately available terminal result. Settlement means the broker has obtained the successful operation result and the exchange remains attached for response emission; it does not prove peer receipt or an MCP write. Recheck the captured registration's current unexpired identity before that settlement/renewal; never revive it or renew a replacement. Invalid, conflicting, storage-failed or already-detached waits do not renew. The existing independent 10-second heartbeat continues during the 25-second poll; do not extend the 45-second lease or replace heartbeat with admission renewal.

Registration validity at admission is not authority lasting indefinitely after expiry or release. If the captured registration has expired, been released/replaced or closed before settlement, detach its waiter and do not return a request representation or renew it. For an otherwise writable exchange outside listener shutdown, return the existing registration HTTP `401` envelope; a disconnected exchange needs no reply. Detect loss on registration lifecycle activity and before wait settlement; no new lease sweep timer is required. Registration loss never transfers the waiter to a replacement incarnation or cancels the approval. The retained adapter's existing live-invocation reconnect rules remain applicable.

Install disconnect/abort cleanup before admitting the waiter, and recheck detachment inside queued admission before installing it or processing its deadline. Pre-aborted/pre-disconnected exchanges shall install no waiter or timer and perform no deadline mutation. Disconnect racing admission or expiry, a failed clock/identity allocation/append, and every settlement/error/close path shall release only that exchange's waiter, timer and cancellation listeners exactly once. A failed wait shall not leave `WAIT_ALREADY_ACTIVE` stuck. Already-admitted durable writes still obey flush/drain and uncertain-append fencing; detachment neither rolls them back nor fabricates a result. Storage faults use the existing redacted HTTP `500` / `STORAGE_FAILURE`, not a new public code.

Admission/deadline checks shall release the serialized transaction turn before waiting for a future resolution or the 25-second turnover. No poll shall hold that turn for 25 seconds or block unrelated requests, management calls, heartbeats or the expiry sweep. At turnover, serialize the target's deadline/outcome check: return HTTP `200` only for a committed terminal outcome, otherwise HTTP `204` with no body. Resolution racing turnover must be observed either on this poll or the next, never lost between checking state and installing wake observation. Internal `204`/disconnect ends only that HTTP exchange; it does not complete the original MCP call or authorize another call to take its reserved waiter. The adapter shall preserve the original invocation's reservation across turnovers/reconnect and reject overlapping same-request invocations; broker exchange cleanup shall not leak a slot between polls. Private waiter registries, helper APIs and reservation mechanisms remain implementation-owned.

#### Restart, fencing and finite shutdown

Broker restart resets registrations, not durable principal identity or capability verifiers. A retained, open adapter may make one single-flight re-registration attempt on its next implemented tool execution or heartbeat after discovering registration loss. No 1/2/4/8/16/30-second retry loop is required for ordinary registration or a failed reservation operation; surface an honest error when registration cannot be established. That backoff remains specifically required for reconnecting a still-active wait under the earlier cancellation/reconnection contract. Never steal a live registration after a lost create response: `OWNER_IN_USE` may persist until its 45-second lease expires. Re-registration alone shall not replay a business operation or attach a different RPC call to an old waiter.

Registry close is terminal: clear ephemeral entries and refuse subsequent registration, authentication or heartbeat; close cannot reopen the registry. Adapter close/EOF shall first fence new execution, registration and heartbeat work, then stop its heartbeat timer and cancel owned in-flight lifecycle HTTP work. A local generation/serial or equivalent lifecycle fence shall prevent late ensure/heartbeat completion from installing a registration, recreating a timer, scheduling further renewals or releasing another incarnation. Release shall address only the captured registration ID/secret/owner, never the current owner slot by owner ID alone. Timers shall not keep the adapter process alive.

EOF starts cleanup immediately, not after a serialized execution queue drains. Fence queued as well as new executions; they shall not start broker work after close. Cancel the adapter's in-flight ordinary broker HTTP exchanges as well as registration/heartbeat traffic. This is transport cleanup, not an implicit `cancel_approval`: an already-authorized operation may have committed remotely before its exchange was stopped. Do not issue compensating cancellation or replay, infer rollback, mark an unwritten outcome returned, or recover authority by ID/label. A committed preparation whose capability result was lost remains an unused reservation under the earlier lost-preparation rule; a later explicit preparation allocates fresh authority. A caller retaining request authority may later observe/retry only under the existing scoped rules. An explicitly submitted `cancel_approval` may itself commit despite loss of its result; EOF neither creates nor reverses that explicit instruction.

Best-effort release, execution/response drain and all adapter-owned HTTP transport cleanup share a maximum two-second shutdown budget measured from EOF/close, not separate per-operation allowances. Release of captured valid registration authority is the sole permitted new lifecycle HTTP work during close. At that deadline, terminate pending local HTTP requests/sockets and detach timers; waiting on a Promise timeout alone is insufficient. Abort shall destroy the actual request/associated transport, settle affected work and remove cancellation listeners; an already-aborted signal shall not start a request. Repeated close shall not restart cleanup or its budget. Late completions cannot revive the binding. If registration-create committed but its response/authority was lost or shutdown prevented release, the remote registration may remain only until lease expiry; do not claim immediate remote release in that case. No unbounded cleanup retry, durable cancellation, broker shutdown or deletion of a replacement registration is authorized. Private cancellation/clock mechanisms belong to implementation engineering, not a new production test API.

### 4. Durable data and single-winner transactions

The broker is the sole writer. It shall acquire exclusive state-directory ownership before replay or polling and bind the configured port before becoming ready. A second broker shall fail, not share the journal or choose another port. A stale ownership record shall require explicit operator recovery after verifying its owner has stopped; PID reuse shall not justify automatic lock stealing.

#### Pairing replay prerequisite and isolated fixture schema

The portable journal-2 replayer shall recognize the existing pairing mutation vocabulary below before creation can consume paired state. This is not permission to reuse the legacy request/session replayer or accept journal format 1. Each row lists the complete mutation fields, with no additional fields, including inside `pairing`. Hashes are 64 lowercase hexadecimal SHA-256 characters. The following are private storage decoding rules, not new public caller arguments or Telegram sender-validation rules.

- **Identity encoding:** `user_id` and `chat_id` shall be nonempty strings containing only ASCII digits `0`–`9`, with at least one nonzero digit. Retain their exact spelling, including leading zeros; reject numbers, signs, whitespace, fractions, exponents and all-zero strings. No pairing-specific digit-count ceiling is imposed. In particular, a 1–19-digit check neither follows from this contract nor proves signed-64-bit range. Decode without conversion through a floating-point number. This preserves the existing positive-decimal-string domain; it does not authorize arbitrary Telegram payloads. Section 5 still requires actual sender/private-chat validation at the Telegram boundary.
- **Timestamp encoding:** pairing timestamps retain the existing UTC RFC 3339 domain; no single canonical storage spelling is required. A writer may emit `YYYY-MM-DDTHH:mm:ss.sssZ`, but the decoder shall not require that spelling, exactly three fractional digits, or a particular zero-offset spelling. Validate the RFC 3339 calendar/time and UTC offset, rather than accepting everything a permissive date parser normalizes. Compare represented instants, not lexical strings, and do not round fractional seconds in deadline/equality checks. Non-UTC offsets and unknown offset `-00:00` are not UTC timestamps. Preserve stored text; this clarification changes neither other timestamp decoders nor public time inputs.

| Mutation | Exact fields and invariant |
|---|---|
| `pairing.challenge` | `{op,hash,created_at,expires_at}`; unique hash, expiry exactly five minutes after creation; initially unconsumed |
| `pairing.challenge.consume` | `{op,hash,consumed_at}`; targets an existing unconsumed challenge with `created_at <= consumed_at < expires_at` |
| `pairing.set` | `{op,pairing:{user_id,chat_id,paired_at}}`; only while no pairing exists; in the same transaction as exactly one challenge consumption with `paired_at` and `consumed_at` representing the same instant |

**Transaction semantics.** Pairing mutation-array order shall not affect acceptance: resolve challenge declarations, consumptions and the pairing binding as one all-or-none transaction. A consumption must name a unique known challenge, declared in committed history or in that same transaction; duplicate declarations or repeated consumptions fail. A transaction containing `pairing.set` shall contain exactly one set and exactly one consumption, of an unconsumed challenge valid at the recorded consumption instant. A consumption in an earlier transaction cannot authorize a later set. A valid standalone consumption without a set is allowed: it burns that challenge permanently but establishes no pairing. This is replay vocabulary, not authorization for a new burn command, endpoint or writer. Array-order independence here does not change other mutation semantics.

Production pairing shall commit consumption, pairing and the processed Telegram cursor together. Replay shall test challenge validity against recorded `consumed_at`, not recovery time; accepted pairing survives challenge expiry. No transport owner configuration, token or registration grants, removes or invalidates pairing. A second set, even an identical one, fails; no re-pair, removal or reset is authorized.

**A0 private consumer and failure boundary.** Extend the portable core's existing staged `recover()` behavior: validate the entire recovered history before installing any rebuilt reservations, challenge state or pairing. Malformed fields, invalid transitions and unknown mutations fail as `STORAGE_FAILURE` with private diagnostic `JOURNAL_STATE_INVALID`; retain the previously installed in-memory state on failure and expose no partially recovered pairing. On first failed recovery the core remains unrecovered and cannot admit writes. Semantic replay failure shall not append, repair, truncate or otherwise rewrite the journal/history; ordinary framing recovery remains separately governed above and below.

The selected A0 consumer is private in-process `broker.pairing()`: return `null` when no pairing has been successfully recovered, otherwise a fresh record containing exactly `{user_id,chat_id,paired_at}` with the stored values. Mutating that returned record shall not alter internal state. Challenges, hashes and consumption records are not returned. This follows the existing portable core's private copied-view pattern; the getter is an A0 addition, not an assertion that it already exists. Pairing shall not be added to `status()`, `snapshot()`, HTTP status or MCP output. A0 adds replay and this consumer only: no pairing writer, route, CLI behavior, legacy replayer reuse or Telegram processing, and no production testing API. Existing reservation authority and replay invariants remain unchanged.

An enabling test may prepare an isolated, test-owned, protected state directory through normal setup, then, **with its broker stopped and no ownership record**, use the existing `Journal.open` / `append` / `close` storage interface to append a synthetic challenge transaction followed by its consumption-plus-pairing transaction. Use the exact schema above, a synthetic code hash, synthetic private user/chat IDs and valid timestamps; never write plaintext codes/capabilities, fabricate framing/checksums, overwrite a live journal or alter ordinary operator state. This fixture needs no Telegram cursor because it consumes no Telegram update. Start the actual broker only after closing the fixture writer. Its production replay must establish the pairing before any request is submitted. Production shall not import the fixture or expose a seed/reset route, CLI option or decision API.

This fixture establishes a **previously paired state prerequisite**, not pairing authorization or first-use proof. It shall contain no approvals, human outcomes, requests or delivery reports. Separate clean-state denial tests shall retain no pairing. Public empty-state pairing/private-chat validation require their own controlled production-path proof. Supplied manual first-use evidence is recorded in Context, not established by this fixture. Further real token use/human interaction requires separate authorization. Preseeded success cannot satisfy either proof category. Other request/journal encodings remain implementation-owned and must be pinned for test decoder bindings before their proof consumes them.

**Startup and refusal contract.** Exclusive state ownership shall precede opening the journal for recovery, replay, tail truncation, or any journal mutation. Owning the configured listener alone does not establish ownership of the state directory. Acquisition shall exclude concurrent starts against that directory, including starts using different configured ports. An existing ownership record, whether apparently live, stale, malformed, or of uncertain provenance, shall not be replaced by startup. A dead PID, an available port, or unreadable record contents are not permission to recover ownership. Refusal shall preserve the existing record byte-for-byte and leave the journal unchanged; unavailable ownership exits `3`, while storage/integrity failure exits `4`. Partial-start failure and shutdown shall release only ownership demonstrably acquired by that invocation, never unconditionally delete another invocation's record. The private locking mechanism and ownership identity representation belong to implementation engineering.

**Operator recovery boundary.** Explicit stale-owner recovery is required, but no recovery command, force flag, or destructive removal procedure is authorized by this design. The safe no-new-flag correction above shall proceed independently; a stale record may legitimately block restart. Graceful shutdown shall release its own ownership after journal activity has stopped. Abrupt-stop restart tests must distinguish this required refusal from successful recovery; they shall not silently clear ownership to obtain a passing replay result.

**Recovery proposal — requires a scoped user decision before execution.** A possible stopped-state administrative procedure is: identify the exact state directory and ownership record; prevent concurrent starts; independently verify the owning broker and its journal users have stopped (PID absence or port availability alone is insufficient); retain a protected backup of the entire stopped state and original ownership record; explicitly remove only that verified stale ownership record; then start normally and acquire fresh exclusive ownership before replay. Any uncertainty shall stop the procedure without modifying state. Approval would enable only this record removal for the named stopped state, not journal deletion/repair, permission changes, killing an unknown process, automatic stale replacement, or exited-OpenCode recovery. The executor and means of excluding concurrent starts require review before execution; no new CLI is selected here. Existing authorization for teardown of a wholly run-owned test namespace is not authority to recover ordinary operator state.

Persistence shall be a versioned, checksummed append-only transaction journal on a local filesystem. Each committed transaction contains a monotonic sequence, its complete mutations, byte length, and integrity checksum. Completion requires a full record and successful file flush before any corresponding acknowledgement or external effect. No in-memory-only approval or offset advancement is permitted. On restart, replay committed records; discard only an incomplete final record, and stop on a checksum failure, sequence gap, unsupported version, or corruption before the tail. Never silently reset to empty state. Journal creation and recovery shall establish the required filesystem durability before reporting readiness; interruption and disk-full behavior require OS-specific tests. Compaction and automatic history deletion are deferred; operators back up the stopped broker's entire state directory.

Logical entities and invariants:

| Entity | Required durable fields / uniqueness |
|---|---|
| Pairing | One `{user_id,chat_id,paired_at}`; Telegram numeric IDs stored losslessly as decimal strings; consumed challenge hash and expiry, never a reusable plaintext challenge |
| Owner | Immutable transport-principal `owner_id`, operator label, protected credential reference; never a credential value or inferred agent identity |
| Prepared handle | Immutable `owner_id`, `request_handle`, reserved `request_id`, `capability_hash`, display `session_label`, `prepared_at`; at most one bound request, no plaintext capability |
| Request | Common representation above; immutable owner/handle binding, effective duration, unique handle-scoped idempotency key, pairing identity snapshot |
| Resolution | At most one per request: type, accepted time, deciding user/chat, source Telegram update ID, exact response text if any |
| Telegram presentation | Request message IDs and reply-prompt IDs scoped by chat; callback tokens; durable `response_opened` flag; pending send/edit/acknowledgement work |
| Delivery ledger | One per terminal resolution: stable `decision_id`, exact outcome payload, returned/acknowledged timestamps and status; no OpenCode prompt ID or HTTP admission |
| Enhanced delivery intent | Human resolutions only; same owner/request/decision identity, capability status and redacted failure; no event wire payload until sourced and approved |
| Poll cursor | Last fully processed `update_id`; advance only in the same transaction as the update's durable consequences |
| Compatibility evidence | Tested MCP/runtime/harness versions and configuration references; diagnostic only, never ownership authority |

For each pending resolution attempt, the serialized transaction shall sample broker time and first test `now >= expires_at`. If true, commit `expired`; otherwise the first valid approve/reject/response/cancel wins. `Respond` button selection is not a resolution. Terminal resolution commits its stable decision identity and exact outcome payload together; human outcomes also create enhanced delivery intent. After commit, expiry/cancel/replayed/conflicting updates cannot replace it. Accepted outcomes remain retrievable after expiry. Expiry/cancellation create no approval or human-decision event intent but shall return their closure to a live waiter.

**Expiry cannot be deferred past creation/read implementation.** The first actionable request writer/replayer shall also write and replay terminal expiry, its stable `decision_id`, exact closure payload and initial delivery ledger in one flushed transaction. Creation replay, read, status and later wait/resolution use this same serialized deadline rule; return the post-commit representation, never a synthesized terminal result or stale pending state at/after the deadline. A flush failure returns `STORAGE_FAILURE`, not successful expiry. The healthy one-second sweep and restart deadline processing shall exist before public creation/read is enabled. Replay retains terminal identity/payload and never expires a previously accepted decision. Expiry-only tests may use a controlled private clock plus actual journal recovery; public boundaries separately prove persistence and no premature receipt. No cancellation, Telegram or later delivery checkpoint may be the missing writer/replayer needed to make an early read safe.

#### Live-waiter ordering and initial delivery

**G3 — register before admission-triggered expiry.** Inside serialized admission of an authorized, healthy, attached wait, first reject an existing waiter, then install this waiter's wake observation, then sample/apply the target's deadline. Thus a pending request first found due by this admitted wait commits expiry with initial `delivery_state:pending`, not `unavailable`. Check and subscription shall have no missed-wake gap. An already committed terminal request returns its unchanged representation; attaching a wait shall not rewrite its original ledger or allocate another decision.

Every terminal writer shall select its initial ledger from live reachability when constructing the serialized resolution mutation before append: a matching, attached, admitted waiter with its captured registration still valid yields `pending`; no such waiter and no verified enhanced path yields `unavailable`, with `delivery_error:null`. An original invocation's reservation between internal polls prevents takeover but alone is not an attached broker waiter or evidence of receipt. This rule applies to cancellation and expiry now and human resolution when implemented; it grants no human-outcome implementation or proof. If another serialized operation resolved first without a live waiter, a subsequent wait observes that initial `unavailable` unchanged. These are different ordered histories, not equivalent persisted outcomes.

Flush and install the terminal resolution, stable decision ID and initial ledger together before waking a waiter with the terminal representation or returning terminal HTTP success. Wake every matching attached wait after successful installation, whether the writer was wait admission, authorized read/cancel, status or a broker sweep; a wake signal alone shall not carry an uncommitted outcome. Detachment or registration loss during an already-admitted append does not change its selected mutation, undo its commit or justify a second ledger mutation. The persisted initial `pending` therefore is delivery intent at resolution, not a receipt guarantee. A failed/uncertain append shall settle affected waits as storage failure rather than wake them with a synthesized terminal result; retain the journal-wide fence. Neither waiter installation, internal `200`/`204`, transport detachment nor a wake records `returned` or `confirmed`; section 6's actual-write/acknowledgement rules alone supply that evidence.

##### A1a-ii selected private creation boundary

The selected ordinary method is `createRequest({ownerId,capability,requestHandle,clientRequestId,action,context,expiresInSeconds}={}) -> Promise<null|{created,request}>`. `created` is boolean: true only for this call's successfully flushed new creation, false for an identical existing creation; `request` is an independent common representation, including nested copies. Null is the private authority-denial sentinel, not a public success; future HTTP wiring maps it to `404` / `NOT_FOUND`. No route or MCP execution is enabled by this selection. Private helper placement, including a `NOT_PAIRED` helper versus ordinary `BrokerError` construction, remains implementation-owned.

For a recovered, open, healthy core, admission and serialized effects shall follow this order:

1. Require an object under the existing private plain-object convention. Omitted/undefined arguments use the empty default object; explicit null, arrays and other non-objects reject as private `INVALID_ARGUMENT`, `exitCode:2`, never a raw destructuring/coercion error. Validate `clientRequestId`, action, context and duration against section 3 before capability checks. Only undefined duration defaults to `3600`; explicit null, noninteger, string or out-of-range duration is invalid. Required context has no implicit empty-string default. These field refusals use the same private invalid-argument classification.
2. Require a configured string `ownerId`, an explicitly supplied string `requestHandle` matching the handle encoding, and a well-formed string capability verifying that exact reservation/principal/handle tuple. Missing, undefined, malformed, unknown, foreign, revoked or mismatched authority returns null without queue admission, current-time sampling, pairing disclosure or mutation. Calling `authorize()` with an omitted optional binding is insufficient. Extra private object properties may be ignored, but shall never override inherited IDs, owner, prepared label, pairing snapshot, timestamps or initial state. Public no-additional-properties validation remains unchanged.
3. Inside the serialized turn, inspect the authorized handle's existing creation before sampling time or constructing a new request. Compare the exact unnormalized client key/action/context and effective duration. Any difference rejects with ordinary `BrokerError`, `status:409`, `code:IDEMPOTENCY_CONFLICT`, `retryable:false`; it samples no time and expires/appends/installs nothing, even if due. An identical retry returns `{created:false,request}` through the accepted target-only expiry path: pending targets sample time inside serialization and flush any due expiry before returning; terminal targets retain their exact outcome without time sampling or append. It never recomputes or extends the creation deadline. Concurrent identical calls shall produce at most one creation mutation; a queued follower observes that creation rather than appending another.
4. For a handle not yet created, test whether committed pairing exists before accessing its fields. If absent, reject with `BrokerError`, `status:503`, `code:NOT_PAIRED`, `retryable:false`, and exactly `No human is paired; run proceed-mcp pair and complete private-chat pairing`. Allocate no deadline and sample no current time. This check shall not dereference a null pairing. Pairing and reservation must already be committed before the creation transaction, under the earlier-transaction rule above.
5. Sample actual creation time inside serialization, derive the effective deadline and validate its strict instant/duration/lower-bound invariants. Copy the exact committed reservation label and private pairing snapshot. Measure the complete production presentation using the accepted plain-text bound and actual timestamp spelling before append. Caller-field or complete-rendering refusals are `INVALID_ARGUMENT` / `exitCode:2`; an unusable clock or unrepresentable generated time is `STORAGE_FAILURE` / `exitCode:4`, not a caller error. Timestamp/rendering admission may therefore consume this clock sample; it is not universally clock-free. All these pre-append refusals leave journal bytes/sequence, reservation and request state unchanged and allocate no decision, callback, waiter or presentation work.
6. Append the exact `request.create` mutation, await the real journal flush, then install the complete pending request and return `{created:true,request}`. Before successful flush, no observer or result may expose the new request. Inherited values and initial states remain exactly those specified above; extras supply no replacement authority or state.

##### Uncertain append and recovery fence

An append/write/sync rejection is `STORAGE_FAILURE`, not evidence of rollback: it may leave no frame, an incomplete tail or a complete frame whose durability was not acknowledged. Do not install the failed transaction, report creation/expiry success, retry its append automatically, delete its frame or fabricate compensation. The last installed snapshot may remain available as a copied last-acknowledged view, not proof that no additional frame exists.

Before the serialized turn releases after an uncertain append, fence further journal writes and successful deadline-aware observations for that journal. A per-handle fence alone is insufficient: the append sequence and possible incomplete tail are shared, so even an unrelated reservation or expiry could corrupt history. Queued duplicates and other queued work shall recheck the fence at execution and reject as storage failure without clock sampling, append or success; fresh work shall not bypass it. Argument/authority denials remain non-disclosing. This uses the existing storage-failure classification, not a new prerequisite/public error or a rollback guarantee.

Only successful exclusive storage reconciliation and whole-history semantic recovery may clear the fence. Quiesce journal users; reconcile framing/sequence through the storage owner's normal close/reopen recovery, discard only an incomplete final frame under the existing framing rules, and establish required durability before acknowledging recovered mutations. Calling the present read-only `Journal.recover()` alone does not establish tail repair or successful sync and is insufficient for an uncertain write. A retained complete valid creation is recovered once and an explicit identical retry returns `created:false`; if no complete creation survived, a later explicit retry may create once under the same reservation. Retained expiry keeps its exact decision identity. Corruption or failed recovery retains the fence and previously installed state; no writes or partially rebuilt state become admissible. Recovery shall not race queued operations, and replay itself remains clock-free. No stale-lock removal, administrative repair/reset or automatic business replay is authorized.

Replay shall stage reservations, pairing, requests, decision uniqueness and ledger state across the entire history before installation, extending A0's fail-closed boundary. Invalid field types, extra/missing fields, snapshot mismatch, early/duplicate expiry, duplicate creation/decision IDs and unknown operations yield `STORAGE_FAILURE` with private diagnostic `JOURNAL_STATE_INVALID`; retain installed state and journal bytes. First failed recovery admits no writes. Semantic recovery itself shall not append expiry: after successful replay, a separate serialized production expiry pass handles due pending state. Before public readiness, that pass shall flush successfully; historical validation failure shall never be repaired by a current-time sweep.

**Observation timing.** A1a's ordinary request read and status observation shall await serialized due-expiry commits before returning their representations; failure returns storage failure, not stale pending success. An in-process redacted snapshot may be a synchronous committed-state view and is not a deadline-processing operation or public readiness proof. A1a may expose recovered seeded requests through the existing control status consumer; that consumer must use the truthful representation/deadline behavior immediately, not wait for A1b to remove a fabricated empty list. The incomplete alpha checkpoint instead refuses request-bearing status under section 7's explicit temporary contract; it cannot satisfy this successful-observation requirement. With reservations only, existing empty-request observations remain unchanged. Until A2, cancellation/acknowledgement/returned shall not report success or mint outcomes/ledger evidence; the reserved-only denial checkpoint is not evidence of implemented actionable management. Their positive contracts are enabled and proved in A2, not by a test fixture. The existing temporary pairing/retry diagnostics remain independent.

An update replay at or below the committed cursor has no new decision effects; callback acknowledgement may be repeated. Each update shall still be validated against pairing and request state. Process updates in increasing ID order; do not require contiguous IDs. Advance the next `getUpdates` offset to the committed ID plus one, never to the end of an uncommitted batch. Sweep pending deadlines at least once per second while healthy, and expire requests against current time before applying backlog after restart. Their maximum 24-hour lifetime matches Telegram's update-retention ceiling without pretending that offline updates are guaranteed.

**Alternatives rejected:** independent JSON overwrites lose atomic resolution/ledger/cursor ordering; a separate database daemon or native add-on complicates clean cross-platform installation. The journal is deliberately single-writer and small-scale, not a general database abstraction.

#### A1b runtime scheduling and failure policy

Startup order shall be protected-state/configuration validation and exclusive ownership, journal open/recovery, whole-history semantic replay, awaited serialized expiry sweep, configured loopback bind, final protection verification, local readiness, then periodic scheduling. The initial sweep must flush all due groups before binding; failure never listens or announces readiness and cleans up only this invocation's listener/core/journal/ownership. A pre-listen `503` is not reachable public evidence; a separately bound but not-yet-ready listener may exercise the existing readiness guard only.

While healthy, schedule sweep attempts every `1000` milliseconds using a timer that does not keep the process alive. At most one scheduled sweep may be outstanding, including queued core admission; skip overlapping ticks without a backlog or catch-up burst. A blocked serialized writer or event loop can delay completion; the cadence is not a one-second durability SLA. Every deadline-aware request still applies its own serialized expiry rule.

On a scheduled sweep failure, stop further ticks and log once a fixed redacted diagnostic: `expiry scheduling stopped after a storage failure; stop and restart serve`. Do not include exception text, paths, request content, capabilities or pairing data. Retain the listener for authenticated observation, not as a healthy-broker claim. An uncertain append retains the existing journal-wide core fence. A scheduler failure before append does not itself prove an uncertain write; nevertheless latch runtime deadline-processing failure so control status and otherwise-authorized creation/read/preparation refuse with the existing redacted HTTP `500` / `STORAGE_FAILURE` envelope rather than advertise successful healthy operation. Preserve browser/authentication/role/input/authority denials before this operational refusal; disclose no request details. No new public health route, status field or error code is introduced. Listener-bound/startup-ready means transport admission only, not continuing storage health; any in-process readiness observation claiming current operational health must become false after this failure. Status must not return a stale last-acknowledged snapshot as successful health. Ephemeral registration maintenance is not journal-health evidence.

**SCHED-FAILURE-001 — failure ordering.** A failure of the actual scheduled sweep, including a pre-append clock/validation rejection, shall install the operational deadline-failure latch before that failed serialized turn releases already-queued authorized followers. Those followers shall recheck the latch before sampling time, allocating identities, mutating or reporting success. A scheduler's external Promise rejection handler after core queue release is not sufficient. The scheduled-work/core integration owns this ordering; its private seam remains implementation-owned. This requirement does not make every ordinary direct core sweep/read/status pre-append rejection a permanent operational failure. Uncertain append fencing remains mandatory for every caller independently of scheduling.

The operational latch is idempotent, performs no append/expiry and cannot be cleared in place. It is distinct from the uncertain-append fence and shall not replace that fence or change its existing precedence. In particular, preparation retains existing fence/closed/unrecovered refusals; for a recovered open core without that prior refusal, validate the configured owner and effective session label (including an explicitly empty label) before the new operational refusal. Creation/read retain their existing input/authority denials before the new refusal. Already-admitted work held in an actual append/sync drains normally: a successful flush may install and return its committed result, with no rollback or compensating mutation. Work merely queued behind a failure is not already admitted in this sense.

**Synchronous failure hooks.** In this cut, the selected scheduler calls `onFailure()` once with zero arguments and calls `logger(message)` once with only the fixed diagnostic above. These are synchronous notifications, not asynchronous coordination. On failure, permanently disable scheduling and establish the core latch/current-health false independently of either user callback; then attempt `onFailure`, then the logger. Contain each synchronous throw separately so neither suppresses the other attempt, revives scheduling, replaces the storage failure or prevents shutdown settlement. A throwing logger means one diagnostic attempt, not guaranteed output. Do not recursively log callback failures or add error details. Ignore ordinary return values. If either callback returns a Promise/thenable, observe and contain its rejection without awaiting its settlement; fulfillment/rejection shall have no scheduling, readiness or stop effect. No unhandled rejection attributable to that returned value is permitted. Required latch/readiness changes shall be synchronous and shall not depend on work deferred by a callback. No asynchronous notification/delivery guarantee, retry, new dependency or public configuration knob is authorized.

No automatic restart, fence clearing, append retry, corruption repair or reset is authorized. Runtime stop shall synchronously set current-health `ready` false when first called; it remains false through drain, completion and late callbacks. Shutdown first stops scheduling and awaits any in-flight sweep, then closes listener/registrations, drains the core, closes the journal and releases only owned state ownership. Scheduler stop and runtime stop each return their own same shared Promise on repeated calls, including after settlement, not an early or separately wrapped completion. Scheduler stop fulfills once the outstanding sweep has settled and synchronous failure-hook attempts are complete, even if the sweep rejects or a hook throws; callback-returned Promises do not extend this drain. Runtime stop shall still perform its ordered cleanup despite those failures. No tick or late completion may enqueue work after scheduler stop or touch closed storage. Private scheduler module/signature and failure-latch placement remain implementation choices within these ordering constraints.

**G2 — listener shutdown with live waits.** At listener close, fence new wait admission, close registrations and detach all outstanding wait exchanges, destroying their associated transport where needed to settle them without waiting for the 25-second poll timers. Remove their timers/listeners; do not fabricate `200`, `204`, a human outcome or a business cancellation. This scoped transport destruction applies to wait exchanges, not a blanket destruction of active ordinary HTTP requests. Preserve the existing drain of already-admitted non-wait operations, including actual append/sync and committed-result response handling; no rollback or compensating operation is authorized. A shared transport shall not be destroyed in a way that discards such an ordinary operation's required drain. Listener close must not depend on future poll ticks, and no late wait completion may renew registrations, recreate timers or touch closed storage. The runtime's scheduler → listener/registrations → core → journal → ownership cleanup order remains unchanged; the adapter's two-second budget is not a new broker-wide write deadline.

Accept pairing only when `message.from.id` is present, `chat.type` is `private`, the challenge is valid/unconsumed, and no pairing exists. Persist both sender and chat IDs. Limit failed code attempts to five per sender per minute; do not disclose challenge or request details. Re-pairing is not an automatic incoming-message operation; loss/change of the paired human requires a separately authorized local administrative procedure, not a fallback identity.

The dedicated poller shall call `getUpdates` with `timeout:30`, `limit:100`, and `allowed_updates:["message","callback_query"]`; HTTP timeout shall exceed polling timeout (40 seconds). Unsupported stale update types are harmlessly consumed. Check Telegram's `ok` envelope, not HTTP status alone. Obey `parameters.retry_after` for rate limits; otherwise retry transient failures with bounded backoff of 1, 2, 4, 8, 16, then 30 seconds. Poller conflict/webhook diagnostics shall stop competing polling and require operator repair. `getMe` checks token identity; `sendMessage` returns the message ID used for durable presentation mapping.

Request messages shall use plain text (no `parse_mode`) and show the full request ID, owner ID, prepared session label (explicitly caller-supplied display context, not verified identity), action, context, UTC expiry, resolution, and separate delivery status. Render at most 4096 characters; inputs that cannot fit shall be rejected before creating a request. Use `InlineKeyboardMarkup` with Approve, Reject, Respond buttons. Callback data shall be `a:<token>`, `r:<token>`, or `t:<token>`, where the token is 32 random hexadecimal characters mapped durably to one request; this is below Telegram's 64-byte limit. Tokens are correlation, not authority.

For every callback, check `callback_query.from.id` against the paired user and its message's private `chat.id` against the paired chat. Also check the stored callback token and originating message ID. Missing/inaccessible message context shall fail closed; `chat_instance` and forwarded request text are not authentication. Call `answerCallbackQuery` for accepted, duplicate, stale, expired, unauthorized, and malformed callbacks when a callback ID exists. Acknowledgement failure never undoes a committed decision; retry best-effort. Unauthorized acknowledgements disclose no request details.

Respond shall durably set `response_opened` before sending a separate plain-text prompt containing the full request ID and `ForceReply {force_reply:true}`. Persist the returned `(chat_id,message_id) -> request_id` mapping. Repeated Respond selections may produce multiple prompts mapped to the same unresolved request; they do not grant authority or resolve it. Accept nonempty `Message.text` up to 4096 Unicode scalar values only from the paired sender/private chat, correlated by a stored `reply_to_message.message_id`. Preserve accepted text exactly, including whitespace and approval-like words. Edited messages, attachments, and uncorrelated ordinary text shall not resolve requests.

If reply context is unavailable, support the explicit command `/respond <request_id> <text>` from the same paired identity, where `<text>` is the exact substring following the single separator after the ID. Require that a Respond interaction has already been opened for this pending request. Conflicting reply mapping and explicit ID shall be rejected. Bare `yes`, a quoted request ID, or multiple possible matches shall never select a pending request. Ask the paired human to use the identified prompt or explicit command without revealing other requests to unauthorized senders.

Commit a valid resolution before confirming it to Telegram; the confirmation shall distinguish “decision recorded” from “session delivery pending.” Retire controls with `editMessageReplyMarkup` and update status with `editMessageText`. Telegram send/edit calls have no documented idempotency key: a crash after send but before recording its ID may duplicate a presentation. All copies retain the same request identity and callback mapping, and can yield only one resolution. An unmapped reply prompt shall not accept text; the paired human can use the explicit response command. Unknown callback message IDs shall not be treated as authority merely to accommodate this crash window.

The waiting sequence shall be: operator configures transport principal → `prepare_approval` returns durable request authority on its own RPC result → capability-authorized `request_approval` commits the request and waits → Telegram presentation → paired-human resolution commit → terminal result on that original waiting `tools/call` → capability-authorized acknowledgement. Delivery status is independent from resolution and shall be monotonic with respect to acknowledgement:

| State | Meaning |
|---|---|
| `not_applicable` | Pending approval, no terminal outcome yet |
| `pending` | Terminal outcome committed, owned delivery not yet confirmed |
| `returned` | Adapter reports successful write of terminal result to the original live MCP response; this does not prove client/model receipt |
| `confirmed` | Request-capability holder acknowledged the matching request and decision ID; not proof of authenticated agent-session identity, execution or useful activity |
| `unavailable` | No live waiter and no verified enhanced path; explicit retrieval requires the retained request capability and principal, never only an ID/label |
| `blocked` | Delivery/storage/auth prerequisite failed; exact decision retained with redacted actionable error |

A capability-authorized acknowledgement may arrive before the adapter's return report and shall not be downgraded by later reports. A result write followed by a crash before reporting leaves delivery uncertain, not failed human resolution. `get_approval` returns the same immutable decision ID and payload; it never schedules agent activity. Acknowledgements are allowed only for capability-authorized, terminal, matching decisions; pending or mismatching decision IDs yield `DECISION_MISMATCH`. A replayed result or acknowledgement cannot create another resolution. Successful writes and acknowledgements are product-level evidence, while useful subsequent agent acknowledgement is a separate live acceptance observation.

#### A2b ledger transition clarification

These rules refine the existing portable ledger; they add no delivery-error producer, historical repair or new delivery path. `delivery_error` describes the current outstanding delivery problem, not the last error ever encountered. Existing committed journal records remain unchanged; recovery applies their transitions without rewriting history.

| Authorized evidence for the matching terminal `(request_id,decision_id)` | Required durable effect |
|---|---|
| First acknowledgement, from any terminal delivery state | Set `delivery_state:confirmed` and `delivery_error:null` together; record the first acknowledgement timestamp. This confirms capability-holder receipt even if the previous state was `unavailable` or `blocked`. Do not invent a successful adapter write or returned timestamp. |
| First successful-write report, including when initial delivery was `unavailable` | Record the first returned timestamp and clear the current `delivery_error`. Set `delivery_state:returned` unless already `confirmed`; retain `confirmed` in that case. Initial unavailability is not a decision conflict and shall not cause HTTP `409`. |
| Repeated acknowledgement or returned report for already recorded matching evidence | Return HTTP `200` with the current representation. Preserve first evidence timestamps, resolution, decision identity and outcome; append no duplicate evidence mutation. A returned report shall never downgrade `confirmed`, and acknowledgement shall never manufacture returned evidence. |

Both first-evidence transitions require serialized append/flush before installation or successful response, with the existing uncertain-append fence and storage-failure behavior. Replay shall recover the same state, null current error and first evidence timestamps, without current-time sampling or a new resolution. Invalid historical transitions retain private `JOURNAL_STATE_INVALID`, exposed only as the existing redacted storage failure. No fixture-written error or returned evidence is needed to make an enabling test pass; existing portable creation/expiry producers still initialize `delivery_error:null`.

Acknowledgement requires the bound owner and request capability, not a registration or a prior return report. Returned additionally requires the live authenticated registration under section 3's validation order; registration alone never replaces request authority. After those checks, a pending request or different decision ID yields HTTP `409` / `DECISION_MISMATCH`, `retryable:false`; missing/foreign request authority retains `404` / `NOT_FOUND`, and invalid registration retains the existing `401` / `AUTH_REQUIRED` classification. No additional waiter-history admission rule is introduced for returned: the broker records an authenticated adapter assertion, not independent proof of an MCP write or client receipt.

The production adapter shall report returned only after its actual successful terminal-result write on the original live waiting invocation, never after an internal HTTP receipt, read, cancellation/acknowledgement tool result, failed/suppressed write or lost call. For the current stdout boundary, successful write evidence requires the stdout write callback to complete without error; constructing a tool result, queueing bytes or obtaining an executor result is insufficient. An initially unavailable ledger may therefore advance when later actual write evidence exists; mere registration or a desire to clear unavailability is not evidence. A direct authenticated HTTP report verifies ledger admission/monotonicity only, not that an MCP response was written. Lost report responses grant no automatic business replay; any explicit repeated report must describe the same actual write and retain the existing authority rules.

#### Successful-write reporting: A1 eligibility, A2 authority and A3 close ordering

**A1 - original-call eligibility, not terminal creation replay.** A new `request_approval` invocation receiving an already-terminal creation replay shall not produce returned evidence, even if its result is written successfully. Capability-authorized access, identical request reuse and a matching request/decision ID do not establish ownership of the original waiting call. A genuine original waiting invocation may receive an immediately terminal wait outcome and report its eligible actual write under A2/A3. No minimum wait duration is required. Matching capability-authorized acknowledgement may independently confirm receipt of a replayed or retrieved terminal outcome, without inventing returned evidence. This distinguishes idempotent request reuse from original-call delivery and adds no new product or security policy.

**A2 - captured authority, one attempt.** A report shall use only the registration ID/secret incarnation captured by the terminal wait that supplied this original invocation's outcome, together with its bound owner, request capability, request ID and matching decision ID. Do not refresh to current registration authority after the stdout callback, re-register for reporting, take over another incarnation or retry a stale/failed/lost report. If that captured authority is locally known to be invalid, suppress the report. Otherwise the broker's existing current-unexpired-registration check decides admission and fails closed on stale authority. The live-wait reconnect ladder does not apply to returned reporting. This clarification does not add broker waiter-history validation or change the accepted HTTP ledger contract.

Reporting shall be a nonblocking, at-most-one automatic attempt per eligible actual result write, using the ordinary tracked, abortable broker HTTP transport. Do not wait for its response before completing the original invocation or allowing unrelated calls to progress. Report success, rejection, transport failure or lost response shall not generate another MCP response, replay a business operation, repeat the result write, compensate a possible commit or fabricate returned/confirmed evidence locally. Observe and settle report failures without unhandled Promise rejections. The existing explicit same-write repeat rule is not an automatic retry service.

**A3 - callback and close ordering.** A successful callback may start that attempt only while the original invocation is still eligible for completion and neither its MCP cancellation nor adapter close/EOF has been processed. Ordering is determined by processing these events, not by guessing when bytes reached the pipe. Cancellation or close/EOF processed before the callback suppresses reporting even if bytes may already be on the pipe. Eligibility checking and attempt admission shall have no deferred gap that permits work to start after a processed cancellation or close. Once admitted, reporting has its own tracked lifetime rather than requiring the completed invocation to remain active. Later cancellation or close/EOF aborts the in-flight report without compensation, duplicate reporting or revival by a late callback/completion. Remote evidence may already have committed before abort, so this remains uncertainty, not rollback.

A stdout callback error or synchronous write throw is failed-write evidence and shall start no report. A backpressure return alone is neither success nor failure: wait for the error-free callback and recheck eligibility. Suppressed writes, error results, pending receipts and results of any tool other than the original waiting `request_approval` supply no returned evidence. Failure of an already-admitted response write shall settle its writer-queue ownership and cleanup without leaving unrelated calls stuck behind a rejected task. Preserve complete, noninterleaved MCP frames for subsequent writes while stdout remains usable. If stdout itself is unusable, fail/close affected work honestly rather than emit a replacement or partial frame, silently retry the failed result or claim the other calls succeeded. Private writer recovery structure remains implementation-owned.

All report waits, actual HTTP abort/transport settlement and response-write drain share section 3's single two-second budget from close/EOF. They shall not postpone cleanup start or extend that budget. No new report may start during close, and late completions shall create no report, registration, timer or response. Private symbols, hooks, callback signatures and queue structure remain implementation choices, not test-only production APIs.

Standard MCP does not provide exactly-once agent execution or atomic knowledge of client receipt. For baseline replay, the client/session must follow stable-decision deduplication instructions; the product shall not independently inject a second turn. If the original call is lost, retain uncertainty and permit scoped observation rather than automatically resend a result on an unrelated call. The enhanced path must solve its stronger duplicate-turn requirement before it is enabled; stable IDs alone are insufficient evidence.
