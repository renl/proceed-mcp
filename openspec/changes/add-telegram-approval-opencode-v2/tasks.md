Payload is `{schema_version:1, sequence, committed_at, mutations[]}` with mutation ops `pairing.set`, `pairing.challenge`, `pairing.challenge.consume`, `request.create`, `request.presentation`, `request.resolve`, `request.delivery`, `request.telegram`, `telegram.cursor`. A resolution and its exact outbox (prompt ID and prompt text) are one `request.resolve` record; a decision-carried Telegram update ID commits in the same record. The pending request representation projects from `request.create`; the outbox projection is `null` until a human `request.resolve` commits.
- **Flush ordering for effect observers**: every transaction is one frame written with `FileHandle.write` on an append handle followed by an awaited `FileHandle.sync()`; the broker applies the mutations and only then answers the HTTP request, sends a Telegram call or admits an OpenCode prompt. Recovery is a second `fsync` after a `FileHandle.truncate` of an incomplete tail (dedicated read/write handle because Windows cannot truncate an append-only handle). Reads compose from replayed state, never from a snapshot.

Response bodies are read from the `IncomingMessage` stream with a 4 MiB bound. The Telegram client is the only `https` user and targets the fixed `https://api.telegram.org` origin. There is no production test flag, injected module hook or test-only route.
