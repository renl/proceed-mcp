## Exact selected private binding and implementation constraints
- Engineering-selected ordinary native seam: `completePairing({code,userId,chatId,updateId}={}) => Promise<{paired:boolean,reason?:'stale'|'rate_limited'|'already_paired'|'invalid'|'expired'}>`. Success is `{paired:true}`, refusal exactly `{paired:false,reason}`. This is a selected implementation binding, NOT a new public API, Telegram parser or production testing interface.
- `code` is the complete raw lowercase 32-hex challenge. `userId` and `chatId` are independently admitted positive decimal strings in design4's lossless domain, including leading zeros and long strings. `updateId` uses the existing raw safe cursor domain. Invalid update IDs reject without mutation. Valid new IDs with invalid code/identity use cursor-only refusal. Stale IDs use no new frame or verification quota. Review these private bindings, not a fabricated raw Update method.
- Future poller owns `RawTelegramUpdate`, non-bot sender, independently validated safe numeric API IDs, private chat and exact `/pair <code>` parsing. Core-B tests cannot prove those facts or require sender/chat equality. That ownership corrects the overbroad future outline in core-A without editing its accepted history.
- Source read: `#replay` currently stages a full local challenge map but retains only `#challengeHashes`, sufficient for uniqueness, NOT consumption validity. `applyPairing` already enforces known/unconsumed challenge and recorded instants. Retain required validity/consumed information after successful replay and issuance, without pinning private field layout. `completePairing` is genuinely absent, the selected implementation target, not an invented substitute for another existing method.
- Reuse the sole queue, health/admission/fence and Journal append path. Inspect state and sample time inside that turn. Valid consumption uses one sampled instant with `created_at <= now < expires_at`, with identical consume/pairing times. No plaintext challenge persistence, failure counter journal, second writer or in-place fence clearing.
- At most five verification attempts per sender in rolling60 seconds, including invalid/expired codes. Changing chat/code cannot bypass the sender ceiling. Other senders remain independent and gain no code authority. Process restart resets only the limiter, never pairing/challenge/cursor history. Already paired never replaces identity or consumes another challenge.
- Successful update writes consume/set/cursor together in one flushed frame. Every canonical newer refusal writes only its cursor. Stale updates append nothing. Install/expose success, pairing and cursor only after append+sync. Queue followers recheck shared uncertainty before sampling or append. Ordinary close/reopen reconciles complete frames, not a read-only recover call.
- Tests compare mutation membership without constraining within-frame order. A0/core-A already own exact decoded schemas, array-order replay and broad whole-history matrices. This packet adds actual consumption writer, limiter, actual-written reopen and first-failed-recovery admission risks only.
- No automatic paired confirmation, network/poller startup or higher-offset request is present here. Tests prove the private cursor cannot supply an uncommitted offset and the result cannot authorize confirmation. Actual poll/confirmation binding remains mandatory later.
