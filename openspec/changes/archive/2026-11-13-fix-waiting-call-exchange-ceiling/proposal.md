## Why

On a supported installed setup, a `request_approval` call can stay open, with the caller's MCP call and transport both active and the request still actionable, and still never return the paired human's decision. The operator resolves the question in Telegram and the agent keeps waiting until its own client timeout arrives with no outcome.

The cause is internal to the product, not caller-side. Read-only source trace at baseline `daf0cf49d4782597b0c5e485165441fdcc6565ae`:

- `src/cli/main.js` builds the adapter's waiting client with `timeoutMs: LOCAL_WAIT_TIMEOUT_MS`, which `src/http/local-client.js` defines as 32,000 ms, described in the source as a waiting exchange that must outlive one broker poll turnover.
- `createSecureLocalClient` turns that value into one absolute per-exchange deadline that starts before the first protected ownership read, charges uncancellable protected reads to it, and refuses any phase whose remaining time is already spent. `secureExchange` repeats that accounting across two more protected-record reads.
- `src/mcp/execution.js` sends `POST /v1/requests/<id>/wait` through that client and only repeats after an exchange ends, so a waiting invocation's progress is gated by that per-exchange budget rather than by the caller.

One measured cost from the ordinary-exchange investigation is relevant but not a waiting-path measurement: protected ownership reads on the affected Windows host cost roughly 11 seconds each and about 33 seconds for one exchange, above the 32,000 ms waiting budget. On such a host one waiting exchange can spend its whole budget on protected work before the broker is reached at all, and the human's decision never surfaces on the waiting call even though the caller is still waiting. That conclusion follows from source and the measured read cost. No runtime measurement of the waiting path exists, and none is claimed.

The requirement question this exposes is not a value choice. The current text fixes what bounds a waiting call: `Portable waiting-call outcome delivery` requires the call to remain waiting while the call and transport remain active and the request is actionable, and its scenario attributes that limit to client execution and transport timeouts, with expiry and explicit cancellation returning their non-approval closure. Nothing in the current text authorizes a product-internal duration ceiling to end that wait. The ordinary-exchange correction examined this path, left it deliberately untouched, and recorded that settling it is a specification decision to be made here rather than a budget substitution made silently elsewhere.

### Direction Check

- Subject: the operator and their agents, on a supported installed setup, waiting for a decision on a request that is still actionable against the protected local broker they configured.
- Desired outcome: the waiting MCP call returns the paired human's actual outcome while the caller's call and transport remain active, instead of the wait ending on a product-internal duration.
- Threat or problem: a product-internal exchange budget, spent on protected work before any outcome can be read, ends the wait while the caller is still waiting, so a real human decision is never delivered to it.
- Confirmation: the change addresses that subject and that threat directly. It removes a product-internal duration from the set of things that may end an actionable wait and leaves the caller's own limits and the request's disclosed expiry as the only bounds. It raises no documented caller-side limit, weakens no admission, ownership, key, identity or protection check, and does not move work onto the person resolving approvals or onto the harness.

## What Changes

Outcome in one line: no product-internal exchange, attempt, poll or command duration ceiling may end a waiting call while the caller's call and transport remain active and the request is actionable, so the caller's own client execution and transport timeouts and the request's disclosed expiry bound the wait and nothing shorter does.

- One requirement meaning changes, in `opencode-session-continuation`: what may bound a waiting call. The requirement statement of `Portable waiting-call outcome delivery` gains the explicit prohibition, its scenario `Return actual outcomes within documented waiting limits` names the caller-side limits and the request's disclosed expiry as the bounds, and one scenario, `Waiting call outlives internal durations`, states the obligation as an observable outcome. Every other requirement and scenario in that capability, and every requirement and scenario in `telegram-approval`, keeps its current text unchanged.
- Preserved exactly and stated in the delta: a client or transport timeout does not cancel the durable request. Pending or timed-out state grants nothing. Expiry and explicit cancellation still return their non-approval closure. Failures are never reported as human decisions or as successful delivery. No automatic resumption, no event-driven wake-up, no retry framework and no indefinite-wait promise is added.
- The existing documentation obligation remains in force and keeps its meaning: the product documents the caller-side limits and the request's disclosed expiry without promising indefinite waiting. This change introduces no new documented numeric limit and raises none, so no documented value changes.
- Acceptance is not met by substituting a larger internal constant. A product-internal ceiling large enough for one host's protected reads is still a product-internal ceiling, and the requirement is about what may bound the wait at all, not about which number is chosen. Picking a bigger number would leave the same failure reachable on a slower host and would still let an internal timer, rather than the caller, decide when an actionable request stops being waited on.
- Independently landable against `main` at `daf0cf49d4782597b0c5e485165441fdcc6565ae`. No stacked parent and no dependency on another active change, including the ordinary-exchange correction, which touches different call sites and a different contract question. One change, one PR, with the authorized archive inside it.
- This is an exposed behavior correction of an existing user-visible wait, not unexposed foundation work. Its user-visible value is that a paired human's decision reaches the call that is still waiting for it on a host whose protected read plus handshake cost exceeds what the old internal waiting duration left available and still fits the ordinary exchange budget, so the request is created and the wait begins. On a host where that cost also exceeds the ordinary exchange budget, the request-create or registration exchange can fail before the wait starts, and this change does not fix that host end to end.
- Excluded on purpose: error classification and public failure wording, README wording, retries and any retry or reconnection framework, logging, captured child output, state, credentials and provisioning, pairing, security policy, every other budget and subcap, and unrelated refactors.

## Acceptance Outcomes

Implementation-independent and binary. Each is either met or not met, with no partial credit and no alternative interpretation.

- **AO-1 The outcome reaches a waiting call despite slow protected work inside the waiting exchange.** GIVEN a configured, safely owned, matching healthy protected broker whose protected read plus handshake cost inside one waiting exchange exceeds what the old internal waiting-exchange duration left available for that work, and an actionable request whose caller's call and transport remain active, WHEN the paired human resolves it, THEN that same waiting call returns the matching human outcome. Met only if the outcome is returned on that call. The internal duration this outcome removes is the waiting exchange's own; the outcome neither requires nor assumes that the request-create exchange or the registration exchanges made inside the same invocation exceed their own ordinary budget.
- **AO-2 No product-internal duration bounds the waiting exchange.** GIVEN an actionable request and an active caller call and transport, WHEN any product-internal exchange, attempt, poll or command duration that would otherwise bound the waiting exchange elapses, THEN the waiting exchange either keeps waiting or returns the matching outcome, and no expiry, cancellation, failure or other closure is manufactured from that internal duration. Met only if no such internal duration ends the wait. The request-create exchange and the registration exchanges made inside the same invocation keep their existing ordinary exchange budget. That budget is a separate subject, unchanged here, and neither required nor included by this outcome.
- **AO-3 The real bounds still end the wait.** GIVEN the caller's own client execution or transport limit is reached, or the request reaches its disclosed expiry, or its owner explicitly cancels it, WHEN that bound arrives, THEN the wait ends with the corresponding loss or non-approval closure, no approval is recorded, and no automatic resumption, late delivery or successful-delivery claim is made. Met only if the wait ends and reports exactly that.
- **AO-4 The disclosure names the real bounds.** Documentation identifies the caller's client execution and transport timeouts and the request's disclosed expiry as what bounds a waiting call, and makes no indefinite-wait promise. Met only if all three are named and no indefinite wait is promised.
- **AO-5 Durable and single-resolution semantics are unchanged.** A client timeout or lost call does not expire or cancel the durable request, a pending or timed-out request grants nothing, an accepted decision is retained and retrievable under capability-and-principal authority, and one resolution per request still holds. Met only if every one of these still holds.
- **AO-6 No larger internal constant is the fix.** Acceptance is not met by replacing one product-internal duration ceiling with a larger one. Met only if the bound on an actionable wait is the caller's limits and the request's disclosed expiry rather than a product-internal timer.
- **AO-7 A stopped broker is reported honestly.** GIVEN a broker that stops responding while a call is waiting, WHEN the wait ends, THEN it ends at the caller's own limit rather than through an internal capability timer that closes the wait as though the request had closed, and no decision, delivery or approval is claimed. Met only if it ends that way and nothing is invented.
- **AO-8 No new surface for the operator.** No new state, configuration, migration, provisioning step, pairing step, credential read, command, option, tool, or public message wording is introduced. The path from an empty installation to the first approval interaction is unchanged.
- **AO-9 The band this change fixes on its own is stated, not implied.** Acceptance applies to protected read plus handshake cost inside one waiting exchange that falls above what the old internal waiting-exchange duration left available for that work and at or below the ordinary exchange budget. Those two bounds are the whole of what this change resolves. The design derives that band as roughly 7,000 to 10,000 ms of protected read plus handshake cost: above the old 32,000 ms waiting budget less a full 25,000 ms broker turnover, and up to the existing 10,000 ms ordinary exchange budget. Met only if the removed bound is described as the waiting exchange's internal duration, no wider band is claimed for it, and the numeric anchor is presented as a derived illustration rather than as a new limit this change introduces.
- **AO-10 No end-to-end approval is claimed where the ordinary exchange budget still binds.** GIVEN connected protected read plus handshake cost above the ordinary exchange budget, the request-create exchange or a registration exchange can still fail before the wait begins, WHEN that happens, THEN the change is reported as limited to the waiting exchange and not as a working end-to-end approval on that host. Met only if that host is named as still bounded by the ordinary exchange budget and this correction is not presented as an end-to-end approval fix.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

`opencode-session-continuation`, one requirement: `Portable waiting-call outcome delivery`. The delta is included in this change as `specs/opencode-session-continuation/spec.md`.

- **Modified requirement statement.** It keeps its current first sentence verbatim and adds: no product-internal exchange, attempt, poll or command duration ceiling may end the waiting call while the caller's call and transport remain active and the request is actionable.
- **Modified scenario `Return actual outcomes within documented waiting limits`.** Its outcome, authority, and closure clauses are carried verbatim. Only the limit clause changes: the caller's client execution and transport timeouts, together with the request's disclosed expiry, are the bounds, and those are what the product documents without promising indefinite waiting.
- **Added scenario `Waiting call outlives internal durations`.** States the obligation as an observable outcome: a waiting exchange outlasts the product-internal duration that would otherwise bound it, the caller's limits and the request's expiry remain the only bounds, no pending or timed-out state grants anything, no failure is presented as a human decision or successful delivery, a broker that stops responding is surfaced at the caller's own limit with no automatic resumption or late delivery claimed, and the request-create and registration exchanges inside the same invocation keep their ordinary exchange budget as a separate subject rather than one this change resolves.
- **Carried verbatim:** the remaining five scenarios of that requirement, `Prepare private authority before the waiting interaction`, `Prepare then ask and wait`, `Decision before tool completion`, `Request closes while the call is waiting` and `Waiting result is lost but request authority is retained`, and every other requirement in this capability: originating-session delivery, human-intent preservation, continuation after tool timeout, safe pending delivery and replay, honest compatibility, automatic broker availability, shared startup ownership, credential and readiness boundaries, token-disclosure prevention, provisioning fail-closed behavior, credential limitations, confidential admission, legacy upgrade refusal, truthful readiness, first-use and restart, and durable work across automatic startup.

A delta relocates before and after archive, so the delta names that same archived design by repository-relative path instead. Every condition, keyword and obligation in that scenario is unchanged.
- **Unchanged capability:** `telegram-approval`. Its requirements and scenarios already state that a timeout or lost waiting call leaves the request pending until expiry or explicit cancellation, that silence and transport errors imply no approval, and that expiry and cancellation are non-approval outcomes. This change changes none of that text and adds nothing to it.
- **Delta review and archive.** The declared primary spec author of this capability reviews the delta against `openspec/specs/opencode-session-continuation/spec.md` before the single PR merges, and the authorized `openspec archive` applies the reviewed delta. No manual baseline-spec edit is made by this authoring work.

## Impact

- Behavior: what may bound a waiting call. Implementation detail, including which internal values remain and how the wait is structured, belongs to the design and implementation owners. This proposal fixes only the outcome and the disclosure.
- Out of scope with intent: error classification and public failure wording, README wording, retries, logging, state, credentials, provisioning, pairing, security policy, all other budgets and subcaps, and unrelated refactors.
- Independence: no dependency on the ordinary-exchange correction or any other active change. If both land, neither ordering changes this change's outcome.
- First-run state: unchanged. This change introduces no stateful surface and no setup step, so the existing supported path from an empty installation to the first useful approval interaction remains the only path.
- Evidence and limits: this proposal rests on source reading plus the measured protected-read cost recorded by the ordinary-exchange investigation. No runtime measurement of the waiting path exists, no live waiting-call reproduction is claimed, and the unit-only project restriction applies. Independent review establishes that no product-internal duration can still end an actionable wait. Installed operation, Telegram receipt and a real slow-host wait remain unverified until they are actually run, and must not be reported as satisfied by this correction.
- Honest residual limit: with the internal ceiling no longer bounding the wait, a broker that stops responding is surfaced when the caller's own limit arrives, not sooner. The caller therefore waits as long as its own client and transport allow before learning the broker is unresponsive, and the durable request still expires or can be cancelled on its own terms. That trade is accepted deliberately, and it is the reason the documented bounds matter.
